📌 Study Milestones & Checklist

  • Root User Security: Lock root access, do NOT generate access keys, enable Hardware/Virtual MFA.
  • IAM Users & Groups: 1 physical person = 1 IAM user. Groups contain only users (no nested groups).
  • IAM Roles & Instance Profiles: Temporary access for AWS services (EC2, Lambda) and cross-account access without hardcoding secrets.
  • Policy Evaluation Logic: Understand that Explicit Deny always beats Explicit Allow. Default is Deny.
  • JSON Policy Anatomy: Master Version, Statement, Effect, Action, Resource, Condition.
  • Auditing Tools: IAM Credential Report (account user compliance) vs IAM Access Analyzer (identifying public/cross-account shared resources).

🔍 IAM Policy JSON Anatomy

An IAM policy is a JSON document that defines permissions. You must know every key by heart:

{
  "Version": "2012-10-17", // ALWAYS use 2012-10-17 (exam standard)
  "Statement": [
    {
      "Sid": "AllowS3ReadOnlyForSpecificBucket", // Statement Identifier (Optional)
      "Effect": "Allow", // "Allow" or "Deny"
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::my-company-confidential-bucket",
        "arn:aws:s3:::my-company-confidential-bucket/*"
      ],
      "Condition": {
        "Bool": {
          "aws:MultiFactorAuthPresent": "true" // Enforce MFA for access
        }
      }
    }
  ]
}
Exam Tip: Notice that for bucket operations (like s3:ListBucket), the ARN is arn:aws:s3:::bucket-name, but for object operations (like s3:GetObject), it requires the wildcard: arn:aws:s3:::bucket-name/*.

⚖️ IAM Entities Comparison

Entity Who / What is it? Credentials Primary Use Case
IAM User A person or application requiring long-term interaction Console Password / Access Keys (Secret + Key ID) Individual developers/administrators (Least privilege)
IAM Group A collection of IAM users None (inherits permissions to members) Assign identical permissions to multiple users (e.g. Admins, Developers)
IAM Role An identity assumable by anyone/anything that needs it Temporary security credentials via AWS STS EC2 Instance Profiles, Lambda execution, Cross-Account delegation

⚡ Policy Evaluation Hierarchy

The Golden Rule of AWS Authorization:
1. Explicit Deny: If ANY policy says DENY, the final answer is ALWAYS DENY.
2. Explicit Allow: If there is no Deny, is there at least one ALLOW? If yes, ACCESS GRANTED.
3. Default Deny: If there is neither an explicit Deny nor an explicit Allow, ACCESS IS DENIED.

🚨 Real Exam Traps & Clues

Scenario: "An application running on an EC2 instance needs to read and write files to an Amazon S3 bucket. How should security credentials be managed?"

❌ Wrong Answers: Embed AWS Access Keys in the application code; store Access Keys in EC2 User Data; store keys in an EBS volume.
✅ Correct Answer: Create an IAM Role with S3 permissions and attach it to the EC2 instance as an Instance Profile. The AWS SDK automatically retrieves temporary rotating credentials via metadata.
Scenario: "Company A needs to give an external auditing vendor temporary access to inspect AWS resources in Company A's AWS account."

❌ Wrong Answer: Create an IAM User in Company A and email them password credentials.
✅ Correct Answer: Define an IAM Role with Cross-Account Access and require an External ID (to prevent the Confused Deputy Problem).

B) The upload is denied because an explicit Deny in an SCP overrides any IAM Allow.

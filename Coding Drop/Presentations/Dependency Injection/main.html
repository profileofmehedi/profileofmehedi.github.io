সমস্যা

ক্লাস সরাসরি 'new' কীওয়ার্ড দিয়ে ডিপেনডেন্সি তৈরি করে। এটি রিজিড এবং টেস্ট করা কঠিন।

public class Car
{
  private Engine _engine;

  public Car()
  {
    // ❌ Tight coupling!
    _engine = new Engine();
  }
}
সমাধান

ক্লাস ইন্টারফেস ব্যবহার করে, আর ডিপেনডেন্সি বাইরে থেকে ইনজেক্ট করা হয়।

public class Car
{
  private readonly IEngine _engine;

  public Car(IEngine engine)
  {
    // ✅ Loose coupling!
    _engine = engine;
  }
}
মূল ধারণা

Dependency Injection কী?

নিজের প্রয়োজনীয় জিনিস নিজে তৈরি না করে, অন্যের কাছ থেকে চেয়ে নেওয়াকেই DI বলে।

Client
(Car)
INJECTS
Injector
(IoC Container)
CREATES
Service
(Engine)

DI-এর মূল উদ্দেশ্য হলো অবজেক্ট তৈরি করার দায়িত্ব ক্লাসের ভেতর থেকে সরিয়ে বাইরে নিয়ে আসা। Container প্রয়োজনীয় অবজেক্ট তৈরি করে Client-কে প্রোভাইড করে।

প্রকারভেদ

DI এর প্রকারভেদ

ডিপেনডেন্সি ইনজেকশন মূলত তিনটি উপায়ে করা যায়

Constructor Injection
ক্লাসের কনস্ট্রাক্টরের মাধ্যমে ডিপেনডেন্সি প্রোভাইড করা হয়। ASP.NET Core-এ এটিই ডিফল্ট এবং বেস্ট প্র্যাকটিস।

(সবচেয়ে বেশি ব্যবহৃত)
Method Injection
যখন কোনো একটি নির্দিষ্ট মেথডের কাজের জন্য ডিপেনডেন্সি দরকার হয়, তখন মেথডের প্যারামিটার হিসেবে সেটি পাঠানো হয়।
Property / Setter Injection
ক্লাসের প্রপার্টি বা সেটার মেথডের মাধ্যমে ডিপেনডেন্সি সেট করা হয়। এটি সাধারণত অপশনাল ডিপেনডেন্সির ক্ষেত্রে ব্যবহৃত হয়।
জীবনকাল

Service Lifetimes

IoC Container যখন অবজেক্ট তৈরি করে, তখন সেই অবজেক্টের জীবনকাল কতটা হবে?

Transient (অস্থায়ী)
যখনই সার্ভিসটি চাওয়া হবে, প্রতিবার একটি সম্পূর্ণ নতুন অবজেক্ট তৈরি হবে। লাইটওয়েট সার্ভিসের জন্য উপযুক্ত।
Scoped (স্কোপড)
প্রতিটি HTTP রিকোয়েস্টের জন্য একটি মাত্র অবজেক্ট তৈরি করে। ডাটাবেজ কনটেক্সটের জন্য এটি পারফেক্ট।
Singleton (সিঙ্গেলটন)
পুরো অ্যাপ্লিকেশনের লাইফটাইমে একবারই অবজেক্ট তৈরি করে এবং সব রিকোয়েস্টে শেয়ার করে।
মেকানিজম

IoC Container (Inversion of Control)

অবজেক্ট তৈরির নিয়ন্ত্রণ ইউজারের হাত থেকে ফ্রেমওয়ার্কের হাতে।

পর্যায় (Phase) কী ঘটে? উদাহরণ কোড
1. Registration অ্যাপ চালু হওয়ার সময় ইন্টারফেস এবং ক্লাস কন্টেইনারে ম্যাপ করা হয়। builder.Services.AddScoped<IEngine, Engine>();
2. Resolution যখন ক্লায়েন্টের সার্ভিস দরকার হয়, কন্টেইনার ম্যাপ দেখে অবজেক্ট তৈরি করে দেয়। public Car(IEngine engine) { ... }
3. Disposal লাইফটাইম শেষ হলে কন্টেইনার নিজ দায়িত্বে অবজেক্ট ধ্বংস করে। (Automatic)

Tight Coupling Code (সমস্যা)

এই কোডটি মেইনটেইন করা এবং টেস্ট করা অত্যন্ত কঠিন।

public class UserController : ControllerBase
{
  private readonly UserService _userService;

  public UserController()
  {
    // ❌ Bad: Tight Coupling! Dependency Inversion Principle Violation.
    _userService = new UserService();
  }
}
বেস্ট প্র্যাকটিস

DI Code in ASP.NET Core (সমাধান)

Constructor Injection ব্যবহার করে ক্লাসটিকে Decouple করা হয়েছে।

// 1. Program.cs (Registration)

var builder = WebApplication.CreateBuilder(args);

// DI Container-এ সার্ভিস ম্যাপ করা হচ্ছে
builder.Services.AddScoped<IUserService, UserService>();

var app = builder.Build();
// 2. UserController.cs (Resolution)

public class UserController
{
  private readonly IUserService _userService;

  // ✅ Container থেকে Service আসবে
  public UserController(IUserService userService)
  {
    _userService = userService;
  }
}

সতর্কতা

সতর্কতা ও Anti-patterns

DI ব্যবহারে যে ভুলগুলো এড়িয়ে চলতে হবে।

Service Locator Anti-pattern

GetService() মেথড সরাসরি কল করবেন না। সবসময় কনস্ট্রাক্টর ইনজেকশন ব্যবহার করুন।

Over-injection

এক ক্লাসে ৫-৬ টার বেশি ডিপেনডেন্সি থাকলে বুঝবেন ক্লাসটি SRP (Single Responsibility Principle) ভঙ্গ করছে।

Captive Dependency

Singleton সার্ভিসের ভেতরে কখনোই Scoped বা Transient সার্ভিস ইনজেক্ট করবেন না। এতে মেমোরি লিক হতে পারে।

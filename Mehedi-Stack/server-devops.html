সার্ভার ম্যানেজমেন্ট, DevOps ও প্রোডাকশন অপারেশনস

কোড লিখে গিটহাবে পুশ করলেই সিনিয়র ইঞ্জিনিয়ারের দায়িত্ব শেষ হয় না। প্রোডাকশন সার্ভারে শত শত মাইক্রোসার্ভিস কীভাবে ডিপ্লয় হয়, IIS ও Linux Nginx এর ইন্টারনালস, কন্টেইনারাইজেশন এবং লাইভ প্রোডাকশনে মেমোরি লিক বা ১০০% সিপিইউ হ্যাং হলে অ্যাপ না থামিয়ে dotnet-dump দিয়ে সমস্যা খুঁজে বের করার আর্ট এই গাইডে শেখানো হয়েছে।

১. Windows Server ও IIS আর্কিটেকচার ইন্টারনালস

IIS (Internet Information Services) উইন্ডোজের কার্নেল ড্রাইভার HTTP.sys দিয়ে ইনকামিং নেটওয়ার্ক প্যাকেট হ্যান্ডেল করে। এরপর WAS (Windows Process Activation Service) উপযুক্ত Application Pool এর ওয়ার্কার প্রসেস w3wp.exe চালু করে।

In-Process Hosting (৩ গুণ দ্রুত)

ASP.NET Core অ্যাপ সরাসরি w3wp.exe প্রসেসের ভেতরে CLR লোড করে রান করে। এর ফলে কোনো ইন্টার-প্রসেস রিভার্স প্রক্সি ওভারহেড থাকে না। .NET 6/7/8/9 এ এটি ডিফল্ট এবং রেকমেন্ডেড।

Out-of-Process Hosting

IIS শুধুমাত্র রিভার্স প্রক্সি হিসেবে কাজ করে এবং পেছনে একটি আলাদা dotnet.exe প্রসেস Kestrel চালু করে লোকাল পোর্টে রিকোয়েস্ট ফরোয়ার্ড করে। পারফরম্যান্সে সামান্য ওভারহেড থাকে।

AppPool Recycling এর ডিফল্ট ট্র্যাপ:

IIS এর ডিফল্ট সেটিংসে Idle Time-out = 20 minutes এবং Regular Time Interval = 1740 minutes (29 hours) থাকে।

প্রোডাকশন সমস্যা: ২০ মিনিট ট্র্যাফিক না থাকলে প্রসেস শাটডাউন হয়ে যায়, ফলে পরবর্তী ইউজারের রিকোয়েস্ট কোল্ড স্টার্টের কারণে ৫-১০ সেকেন্ড হ্যাং করে! আবার কর্মব্যস্ত দিনে ঠিক ২৯তম ঘণ্টায় অটো-রিসাইকেল হয়ে লাইভ রিকোয়েস্ট কেটে যেতে পারে।
সিনিয়র কনফিগারেশন:
• Idle Time-out (minutes) = 0 (কখনোই স্লিপ করবে না)।
• Start Mode = AlwaysRunning।
• নিয়মিত রিসাইকেলের জন্য স্পেসিফিক টাইম সেট করুন মধ্যরাতে (যেমন ভোর ৪:০০ টায়)।
• Overlapped Recycling এনাবল রাখুন যাতে নতুন w3wp.exe সম্পূর্ণরূপে বুট না হওয়া পর্যন্ত পুরনোটি রিকোয়েস্ট সার্ভ করতে থাকে (Zero Downtime)।

২. Linux সার্ভার ও Systemd ব্যাকগ্রাউন্ড ডেমোন (Daemon)

উবুন্টু বা ডেবিয়ান লিনাক্স সার্ভারে .NET কোর অ্যাপ রান করতে systemd সার্ভিস ইউনিট কনফিগার করা হয়। এতে সার্ভার রিবুট হলেও অ্যাপ স্বয়ংক্রিয়ভাবে চালু হয় এবং ক্র্যাশ করলে সাথে সাথে অটো-রিস্টার্ট নেয়।

/etc/systemd/system/kestrel-api.service
[Unit] Description=Enterprise .NET Web API Service After=network.target [Service] WorkingDirectory=/var/www/myapi ExecStart=/usr/bin/dotnet /var/www/myapi/MyEnterpriseApi.dll Restart=always # ক্র্যাশ করলে ১০ সেকেন্ড পর অটো রিস্টার্ট RestartSec=10 KillSignal=SIGINT SyslogIdentifier=dotnet-myapi User=www-data Environment=ASPNETCORE_ENVIRONMENT=Production Environment=DOTNET_PRINT_TELEMETRY_MESSAGE=false [Install] WantedBy=multi-user.target
Nginx Reverse Proxy ও SSL কনফিগারেশন

Kestrel সরাসরি ইন্টারনেটে এক্সপোজ করা উচিত নয়। Nginx রিভার্স প্রক্সি হিসেবে সামনে বসে SSL টার্মিনেশন, রিকোয়েস্ট বাফারিং এবং সিকিউরিটি হেডার হ্যান্ডেল করে: 

server {
    listen 80;
    server_name api.codex.com;
    return 301 https://$host$request_uri; # HTTPS রিডাইরেক্ট
}

server {
    listen 443 ssl http2;
    server_name api.codex.com;

    ssl_certificate /etc/letsencrypt/live/api.codex.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.codex.com/privkey.pem;

    location / {
        proxy_pass         http://127.0.0.1:5000;
        proxy_http_version 1.1;
        proxy_set_header   Upgrade $http_upgrade;
        proxy_set_header   Connection keep-alive;
        proxy_set_header   Host $host;
        proxy_cache_bypass $http_upgrade;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
    }
}

৩. ডকার মাল্টি-স্টেজ বিল্ড (ইমেজ সাইজ ৮০০MB থেকে ৮০MB তে নামানো)

একজন আন-অভিজ্ঞ ডেভেলপার সম্পূর্ণ .NET SDK ইমেজ রানটাইমে পাঠিয়ে দেয় যার সাইজ ৮৫০ MB। একজন সিনিয়র DevOps লিড Multi-stage Dockerfile ব্যবহার করে SDK শুধুমাত্র কম্পাইল করতে ব্যবহার করেন এবং ফাইনাল রানটাইমকে হালকা Alpine বা Chiseled ইমেজে নামিয়ে আনেন।

Dockerfile (Production Grade)
# ধাপ ১: কম্পাইলেশন ও বিল্ড (ভারী SDK) FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build WORKDIR /src COPY ["MyApi/MyApi.csproj", "MyApi/"] RUN dotnet restore "MyApi/MyApi.csproj" COPY . . WORKDIR "/src/MyApi" RUN dotnet publish -c Release -o /app/publish /p:UseAppHost=false # ধাপ ২: ফাইনাল রানটাইম (সুপার-লাইটওয়েট ও সিকিউর নন-রুট ইউজার) FROM mcr.microsoft.com/dotnet/aspnet:8.0-alpine AS final WORKDIR /app EXPOSE 8080 COPY --from=build /app/publish . USER $APP_UID # রুট ইউজার বন্ধ করা (সিকিউরিটি বেস্ট প্র্যাকটিস) ENTRYPOINT ["dotnet", "MyApi.dll"]
Docker Compose এন্টারপ্রাইজ স্ট্যাক

docker-compose.yml ফাইলে আপনার API Service, PostgreSQL / SQL Server, এবং Redis একটি ইন্টারনাল নেটওয়ার্কে অর্কেস্ট্রেট থাকবে। হেলথ-চেক (HealthCheck) কনফিগার করে নিশ্চিত করা হয় যে ডাটাবেজ রেডি না হওয়া পর্যন্ত API বুট হবে না (depends_on: db: condition: service_healthy)।

৪. প্রোডাকশন ট্রাবলশুটিং: Memory Leak ও Crash Analysis

প্রোডাকশনে হঠাৎ সার্ভারের র‍্যাম ৯৮% এ গিয়ে অ্যাপ হ্যাং করেছে। আপনি সার্ভার রিস্টার্ট দিলে সাময়িক ঠিক হবে, কিন্তু কয়েক ঘণ্টা পর আবার একই সমস্যা হবে। সমস্যার রুট-কজ কীভাবে বের করবেন?

dotnet-dump ব্যবহার করে লাইভ মেমোরি ডাম্প সংগ্রহ ও অ্যানালিসিস

সার্ভার বা ডকার কন্টেইনারে অ্যাপ চালু অবস্থাতেই মেমোরির স্ন্যাপশট সংগ্রহ করুন: 

# ১. .NET প্রসেস আইডি (PID) খুঁজে নিন
dotnet-dump ps

# ২. সম্পূর্ণ হিপ মেমোরি ডাম্প ফাইল সেভ করুন (অ্যাপ বন্ধ হবে না)
dotnet-dump collect -p 4829 -o /tmp/crash_dump.dmp

# ৩. অ্যানালিসিস টুল ওপেন করুন
dotnet-dump analyze /tmp/crash_dump.dmp

ভেতরে জরুরি কমান্ডসমূহ:

  • dumpheap -stat: হিপে কোন ক্লাসের কত লাখ অবজেক্ট এবং কত মেগাবাইট দখল করে আছে তা সাইজ অনুসারে তালিকা দেখায়। (যেমন যদি দেখেন System.Byte[] বা OrderDto ৫ কোটি অবজেক্ট দখল করেছে, লিক সেখানেই!)
  • dumpheap -mt <MethodTableAddress>: সেই নির্দিষ্ট অবজেক্টগুলোর মেমোরি পয়েন্টার অ্যাড্রেস বের করা।
  • gcroot <ObjectAddress>: ম্যাজিক কমান্ড! কে এই অবজেক্টটিকে মেমোরিতে ধরে রেখে GC থেকে বাঁচিয়ে রেখেছে তার সম্পূর্ণ রুট চেইন (Static Event, Singleton List) দেখিয়ে দেয়!
প্রোডাকশনে ১০০% সিপিইউ (CPU Spike) সংকট ডায়াগনোসিস

যখন সিপিইউ ১০০% এ আটকে থাকে, এর কারণ সাধারণত ইনফিনিট হোয়াইল লুপ, রেজেক্স ক্যাটাস্ট্রফিক ব্যাকট্র্যাকিং (Catastrophic Backtracking) অথবা লক কনটেনশন।

সমাধান: dotnet-trace collect -p <PID> --duration 00:00:30 রান করে ৩০ সেকেন্ডের ট্রেস ফাইল নিন। এরপর Speedscope বা PerfView দিয়ে Flame Graph ওপেন করলেই লাল রঙে চোখে পড়বে কোন মেথডটি সিপিইউ সাইকেল গ্রাস করছে!

সার্ভার অপারেশনস পরীক্ষা

উইন্ডোজ সার্ভার IIS এ হোস্ট করা একটি ASP.NET Core অ্যাপ্লিকেশনে ট্র্যাফিক শূন্য থাকার ২০ মিনিট পর প্রথম ইউজার সাইটে ভিজিট করলে পেজ লোড হতে ১০ সেকেন্ড সময় নিচ্ছে। এই সমস্যার কারণ এবং স্থায়ী প্রতিকার কী?

ব্যাখ্যা:

সহীহ উত্তর B! IIS এর ডিফল্ট সেটিংসে ২০ মিনিট কোনো ইনকামিং রিকোয়েস্ট না পেলে রিসোর্স বাঁচানোর জন্য w3wp.exe ওয়ার্কার প্রসেস শাটডাউন হয়ে যায়। পরবর্তী রিকোয়েস্টে কোল্ড স্টার্ট হতে পুরো ডটনেট রানটাইম ও ডিপেনডেন্সি নতুন করে বুট করতে ১০ সেকেন্ড লেগে যায়। Idle Time-out = 0 এবং AlwaysRunning সেট করলে প্রসেস সর্বদা মেমোরিতে ওয়ার্ম অবস্থায় থাকে।

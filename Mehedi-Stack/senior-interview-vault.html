১. Value Type এবং Reference Type এর মূল পার্থক্য কী? মেমোরিতে এরা কোথায় থাকে?

Value Type: সরাসরি ডাটা ধারণ করে এবং সাধারণত মেমোরির Stack এ সংরক্ষিত থাকে। উদাহরণ: int, float, bool, struct, enum, double। যখন একটি Value Type ভ্যারিয়েবল অন্যটিতে অ্যাসাইন করা হয়, তখন পুরো ডাটার একটি স্বাধীন কপি তৈরি হয়। একটির পরিবর্তন অন্যটিকে প্রভাবিত করে না।

Reference Type: মেমোরির Managed Heap এ মূল অবজেক্ট সংরক্ষণ করে এবং Stack এ সেই অবজেক্টের মেমোরি অ্যাড্রেস (পয়েন্টার বা রেফারেন্স) ধারণ করে। উদাহরণ: class, string, object, array, delegate, interface। এটি কপি করলে শুধুমাত্র পয়েন্টারটি কপি হয়, অর্থাৎ উভয় ভ্যারিয়েবল হিপের একই অবজেক্টকে নির্দেশ করে।

নোট: যদি কোনো Value Type কোনো ক্লাসের ফিল্ড বা প্রোপার্টি হয়, তবে সেটিও ক্লাসের সাথে Heap মেমোরিতেই সংরক্ষিত হয়।

২. string এবং StringBuilder এর মধ্যে পার্থক্য কী? লুপের ভেতর কোনটি ব্যবহার করা উচিত?

string হলো Immutable (অপরিবর্তনশীল)। আপনি যখন কোনো স্ট্রিং কনক্যাট বা পরিবর্তন করেন (যেমন str += "a"), C# বিদ্যমান স্ট্রিংটি এডিট করে না, বরং হিপ মেমোরিতে সম্পূর্ণ নতুন একটি স্ট্রিং অবজেক্ট তৈরি করে এবং পুরনোটি আনরেফারেন্সড গার্বেজে পরিণত করে। লুপের ভেতর হাজার বার স্ট্রিং যোগ করলে প্রচুর মেমোরি অপচয় ও Garbage Collection (GC) প্রেসার তৈরি হয়।

StringBuilder হলো Mutable (পরিবর্তনশীল)। এটি ইন্টারনাল ক্যারেক্টার বাফার (Dynamic Array Buffer) ম্যানেজ করে। কোনো নতুন অবজেক্ট না তৈরি করেই বাফারের ভেতর ইন-প্লেস ক্যারেক্টার অ্যাপেন্ড বা মডিফাই করতে পারে।

সিদ্ধান্ত: যদি ২-৩টি স্ট্রিং জোড়া দিতে হয় তবে সাধারণ স্ট্রিং ইন্টারপোলেশন $"Hello {name}" ব্যবহার করা সহজ। কিন্তু যেকোনো লুপ, ফাইল প্রসেসিং বা বড় ডায়নামিক টেক্সট তৈরির ক্ষেত্রে সর্বদা StringBuilder ব্যবহার করা বাধ্যতামূলক।

৩. Interface এবং Abstract Class এর মধ্যে পার্থক্য কী এবং কখন কোনটি ব্যবহার করবেন?

মূল পার্থক্যসমূহ:

  • ইনহেরিটেন্স সীমা: একটি ক্লাস কেবল একটি Abstract Class ইনহেরিট করতে পারে (C# এ মাল্টিপল ক্লাস ইনহেরিটেন্স নিষিদ্ধ)। কিন্তু একই সাথে একাধিক Interface ইমপ্লিমেন্ট করতে পারে।
  • স্টেট ও ফিল্ড: Abstract Class-এ স্টেট (ফিল্ড ভ্যারিয়েবল), কনস্ট্রাক্টর এবং প্রোটেক্টেড মেম্বার থাকতে পারে। Interface-এ কোনো ইন্সট্যান্স ফিল্ড বা স্টেট থাকতে পারে না (শুধুমাত্র মেথড, প্রোপার্টি, ইভেন্টের সিগনেচার)।
  • ডিফল্ট ইমপ্লিমেন্টেশন: C# 8.0 থেকে ইন্টারফেসে Default Interface Method যোগ হলেও তা মূল কন্ট্রাক্ট ডিজাইনের বিকল্প নয়।

কখন কোনটি: যখন আপনি সম্পর্কিত ক্লাসগুলোর মধ্যে কোড শেয়ার করতে চান এবং 'IS-A' হায়ারার্কি তৈরি করতে চান (যেমন Vehicle -> Car) তখন Abstract Class। আর যখন সম্পূর্ণ অসম্পর্কিত ক্লাসগুলোর মধ্যে একটি নির্দিষ্ট চুক্তি বা সক্ষমতা নিশ্চিত করতে চান (যেমন IDisposable, ILogger, IRepository) তখন Interface ব্যবহার করবেন।

C# Internals 🟢 Junior (0-2 Yrs)
৪. Boxing এবং Unboxing কী? এর পারফরম্যান্স ইমপ্যাক্ট কী এবং জেনেরিক্স কীভাবে এটি রোধ করে?

Boxing: একটি Value Type (যেমন int)-কে Reference Type (যেমন object বা কোনো ইন্টারফেস)-এ রূপান্তর করার প্রক্রিয়া। এতে CLR হিপ মেমোরিতে একটি নতুন অবজেক্ট বক্স তৈরি করে এবং স্ট্যাকের ভ্যালু কপি করে হিপে নিয়ে যায়। এটি মেমোরি অ্যালোকেশন ও GC ওভারহেড তৈরি করে।

Unboxing: হিপে থাকা অবজেক্ট বক্স থেকে পুনরায় স্ট্যাকের Value Type ভ্যারিয়েবলে এক্সপ্লিসিটলি ডাটা ফেরত আনার প্রক্রিয়া।

int x = 42;
object obj = x;        // Boxing (স্ট্যাক থেকে হিপে অ্যালোকেশন)
int y = (int)obj;      // Unboxing (হিপ বক্স থেকে স্ট্যাকে ভ্যালু রিট্রিভ)

জেনেরিক্সের সমাধান: C# 1.0 এর ArrayList সব উপাদান object হিসেবে রাখত, ফলে প্রতি ইনসার্টে Boxing এবং রিট্রিভে Unboxing হতো। C# 2.0 এর List<int> জেনেরিক টাইপ সেফটি আনে—যেখানে কম্পাইলার সরাসরি স্পেসিফিক টাইপ হ্যান্ডেল করে কোনো Boxing ছাড়াই, ফলে মেমোরি খরচ শূন্যে নেমে আসে।

C# Fundamentals 🟢 Junior (0-2 Yrs)
৫. C# এর Access Modifiers কয়টি ও কী কী? protected internal এবং private protected এর পার্থক্য কী?

C# এ ৬ ধরণের অ্যাক্সেস মডিফায়ার রয়েছে:

  1. public: যেকোনো প্রজেক্ট বা অ্যাসেম্বলি থেকে অ্যাক্সেসযোগ্য।
  2. private: শুধুমাত্র একই ক্লাসের ভেতর থেকে অ্যাক্সেসযোগ্য (ডিফল্ট)।
  3. protected: একই ক্লাস এবং তার চাইল্ড (ডেরাইভড) ক্লাস থেকে অ্যাক্সেসযোগ্য।
  4. internal: শুধুমাত্র একই প্রজেক্ট/অ্যাসেম্বলির (DLL) ভেতর থেকে অ্যাক্সেসযোগ্য।
  5. protected internal: UNION (OR) লজিক: একই অ্যাসেম্বলির যেকোনো ক্লাস অথবা অন্য অ্যাসেম্বলির চাইল্ড ক্লাস থেকে অ্যাক্সেসযোগ্য।
  6. private protected: INTERSECTION (AND) লজিক: শুধুমাত্র একই অ্যাসেম্বলির ভেতর অবস্থিত চাইল্ড ক্লাস থেকে অ্যাক্সেসযোগ্য। অন্য অ্যাসেম্বলির চাইল্ড ক্লাস এটি পাবে না।
C# Keywords 🟢 Junior (0-2 Yrs)
৬. const এবং readonly এর মধ্যে পার্থক্য কী? কোনটি রানটাইমে ভ্যালু পরিবর্তন সমর্থন করে?

const (কম্পাইল-টাইম কনস্ট্যান্ট): ভ্যালু অবশ্যই ডিক্লেয়ার করার সময়ই দিতে হয়। কম্পাইলার কোড বিল্ড করার সময় ভ্যারিয়েবলের নামের জায়গায় সরাসরি লিটারেল ভ্যালু ইনলাইন (hardcode) করে দেয়। এটি সর্বদা ইমপ্লিসিটলি static।

readonly (রান-টাইম কনস্ট্যান্ট): ডিক্লেয়ারেশনের সময় অথবা ক্লাসের কনস্ট্রাক্টরের (Constructor) ভেতর ভ্যালু অ্যাসাইন করা যায়। রানটাইমে কনফিগারেশন বা ক্যালকুলেশনের উপর ভিত্তি করে প্রতি ইন্সট্যান্সে ভিন্ন ভ্যালু নিতে পারে। কনস্ট্রাক্টর এক্সিকিউট হওয়ার পর এর ভ্যালু আর পরিবর্তন করা যায় না।

৭. C# এ throw বনাম throw ex এর পার্থক্য কী? কেন throw ex প্রোডাকশনে মারাত্মক ভুল?

ASP.NET Core DI 🟡 Mid-Level (2-5 Yrs)
৮. Dependency Injection এ Transient, Scoped এবং Singleton এর সুনির্দিষ্ট ব্যবহার ক্ষেত্র কী?

ASP.NET Core এর বিল্ট-ইন IoC কন্টেইনারে ৩ ধরণের সার্ভিস লাইফটাইম আছে:

  1. Transient (AddTransient): প্রতিবার সার্ভিসের জন্য রিকোয়েস্ট করলেই একটি ব্র্যান্ড নিউ ইন্সট্যান্স তৈরি হয়। লাইটওয়েট এবং স্টেটলেস সার্ভিসের জন্য আদর্শ (যেমন: ইউটিলিটি, ভ্যালিডেটর, ফরম্যাটার)।
  2. Scoped (AddScoped): প্রতিটি একক HTTP Request-এর জন্য একটি মাত্র ইন্সট্যান্স তৈরি হয়। পুরো রিকোয়েস্ট লাইফসাইকেলে যত জায়গায় ইনজেক্ট করা হোক, তারা একই অবজেক্ট শেয়ার করবে। রিকোয়েস্ট শেষ হলে এটি স্বয়ংক্রিয়ভাবে ডিসপোজ হয়। DbContext এবং বিজনেস সার্ভিসগুলোর জন্য এটি সর্বোত্তম।
  3. Singleton (AddSingleton): অ্যাপ্লিকেশন স্টার্ট হওয়ার পর প্রথম রিকোয়েস্টে একবার তৈরি হয় এবং অ্যাপ বন্ধ না হওয়া পর্যন্ত জীবিত থাকে। ইন-মেমোরি ক্যাশ, কনফিগারেশন ম্যানেজার বা সিঙ্গেল ইনস্ট্যান্স ক্লায়েন্টের (যেমন HttpClientFactory বা RedisConnectionMultiplexer) জন্য প্রযোজ্য। এটি অবশ্যই থ্রেড-সেফ হতে হবে।
EF Core & LINQ 🟡 Mid-Level (2-5 Yrs)
৯. IEnumerable বনাম IQueryable এর পার্থক্য কী? Deferred Execution কীভাবে কাজ করে?

IEnumerable: ইন-মেমোরি (In-Memory) কালেকশনের উপর কাজ করে। ডাটাবেজে কুয়েরি চালালে এটি সমস্ত ডাটা মেমোরিতে টেনে নিয়ে আসে এবং মেমোরির ভেতরে ফিল্টার করে (Client-side evaluation)। বড় টেবিলে এটি চালালে মেমোরি ক্র্যাশ করে।

IQueryable: এক্সপ্রেশন ট্রি (Expression Tree) তৈরি করে। এটি WHERE, ORDER BY বা TAKE ক্লজকে সরাসরি SQL স্টেটমেন্টে রূপান্তর করে ডাটাবেজ ইঞ্জিনে পাঠায়। ফলে শুধুমাত্র কাঙ্ক্ষিত নির্দিষ্ট ডেটাই ডাটাবেজ থেকে নেটওয়ার্কের মাধ্যমে মেমোরিতে আসে (Server-side evaluation)।

Deferred Execution (বিলম্বিত সম্পাদন): LINQ কুয়েরি ডিফাইন করার সাথে সাথে এক্সিকিউট হয় না। যখন কুয়েরিটি foreach লুপে ট্রাভার্স করা হয় অথবা ToList() / ToListAsync() / FirstOrDefaultAsync() / Count() কল করা হয়, তখনই কেবল ডাটাবেজে SQL স্টেটমেন্ট রান হয়।

Async Internals 🟡 Mid-Level (2-5 Yrs)
১০. async/await কীভাবে কাজ করে? ConfigureAwait(false) কেন লাইব্রেরি কোডে ব্যবহার করা হয়?

C# কম্পাইলার যখন কোনো async মেথড দেখে, তখন সে মেথডটিকে একটি স্টেট মেশিন স্ট্রাক্টে (IAsyncStateMachine) রূপান্তর করে। যখন await এক্সিকিউট হয়, কলিং থ্রেডটি ব্লক না হয়ে থ্রেডপুলে ফিরে যায় অন্যান্য রিকোয়েস্ট প্রসেস করতে। I/O অপারেশন (ডাটাবেজ বা HTTP) শেষ হলে OS কলব্যাক পাঠিয়ে থ্রেডপুল থেকে একটি থ্রেড নিয়ে বাকি মেথড অংশটুকু চালায়।

SynchronizationContext ও ConfigureAwait(false): বাই-ডিফল্ট await টাস্ক শেষ হওয়ার পর মূল SynchronizationContext-এ ফিরে আসার চেষ্টা করে। ConfigureAwait(false) বলে দেয়: "আমার মূল কনটেক্সটে ফেরার দরকার নেই, থ্রেডপুলের যেকোনো মুক্ত থ্রেডে বাকি কাজ শেষ করো।" এটি লাইব্রেরিতে ডেডলক এড়ায় এবং পারফরম্যান্স বুস্ট করে।

EF Core Optimization 🟡 Mid-Level (2-5 Yrs)
১১. EF Core এ AsNoTracking, Split Queries এবং N+1 কুয়েরি প্রবলেম কীভাবে সমাধান করবেন?

১. AsNoTracking: বাই-ডিফল্ট EF Core ডাটাবেজ থেকে ডাটা পড়ার সময় Change Tracker-এ অবজেক্টের স্ন্যাপশট রাখে। রিড-অনলি এপিআই বা গ্রিড ডিসপ্লেতে .AsNoTracking() ব্যবহার করলে চেঞ্জ ট্র্যাকিং বাইপাস হয়, যা মেমোরি খরচ প্রায় ৪০% কমিয়ে দেয়।

২. N+1 Problem: যদি প্যারেন্ট টেবিল পড়ার পর লুপের ভেতর চাইল্ড টেবিলের প্রোপার্টি রিড করা হয়, তবে প্যারেন্টের জন্য ১টি এবং প্রতি চাইল্ডের জন্য N-সংখ্যক কুয়েরি ফায়ার হয়। সমাধান: .Include(x => x.Orders) দিয়ে Eager Loading করতে হবে।

৩. Split Queries (AsSplitQuery): যখন একাধিক চাইল্ড কালেকশন Include করা হয় (যেমন: Customer -> Orders -> OrderItems), তখন সিঙ্গেল SQL কুয়েরিতে Cartesian Product তৈরি হয়ে মেমোরিতে লক্ষ লক্ষ ডুপ্লিকেট রো জেনারেট হয়। .AsSplitQuery() লিখলে EF Core একাধিক অপ্টিমাইজড সমান্তরাল SQL কুয়েরি চালিয়ে মেমোরিতে ডাটা জোড়া দেয়।

ASP.NET Core Architecture 🟡 Mid-Level (2-5 Yrs)
১২. ASP.NET Core Middleware Pipeline এবং Action Filters এর মধ্যে পার্থক্য কী? এক্সিকিউশন অর্ডার কীভাবে নিয়ন্ত্রিত হয়?

Middleware: HTTP রিকোয়েস্ট পাইপলাইনের সর্বনিম্ন স্তরে কাজ করে। HttpContext রিসিভ করে এবং পরবর্তী মিডলওয়্যারে পাস করে (next()) অথবা শর্ট-সার্কিট করে রেসপন্স ফেরত দেয়। এটি ফ্রেমওয়ার্ক-অ্যাগনস্টিক (Routing, CORS, Authentication, Response Compression)। Program.cs-এ রেজিস্ট্রেশনের ক্রম অনুযায়ী এক্সিকিউট হয়।

Action Filters: এটি MVC/API সাব-সিস্টেমের অংশ। রাউটিং শেষ হওয়ার পর কন্ট্রোলার অ্যাকশন মেথড এক্সিকিউট হওয়ার ঠিক আগে ও পরে রান করে। এর কাছে ActionContext, মডেল প্যারামিটার, এবং ModelState থাকে। ব্যবহার: অ্যাকশন-লেভেল মডেল ভ্যালিডেশন, ট্রানজ্যাকশন হ্যান্ডলিং।

LINQ Deep-Dive 🟡 Mid-Level (2-5 Yrs)
১৩. LINQ এ Select এবং SelectMany এর পার্থক্য কী? Deferred Execution এর সুবিধা কী?

Select (১-টু-১ ম্যাপিং): ইনপুট কালেকশনের প্রতিটি এলিমেন্টকে অন্য একটি অবজেক্টে প্রজেক্ট করে। আউটপুটের দৈর্ঘ্য ইনপুটের সমান থাকে।

SelectMany (১-টু-অনেস্ট ফ্ল্যাটেনিং): যখন প্রতিটি এলিমেন্টের ভেতর নিজস্ব একটি চাইল্ড কালেকশন বা লিস্ট থাকে (যেমন List<Department> এর ভেতর List<Employee>), SelectMany সেই চাইল্ড লিস্টগুলোকে একত্রিত করে একটি সিঙ্গেল ফ্ল্যাট সিকোয়েন্সে (IEnumerable<Employee>) রূপান্তর করে।

Deferred Execution এর সুবিধা: কুয়েরি ডিফাইন করার সাথে সাথে ডাটা লোড হয় না। ফলে একাধিক ফিল্টার ও পেজিং চেইন করা যায় এবং ডাটাবেজে শুধুমাত্র ফাইনাল অপ্টিমাইজড কুয়েরিটিই রান হয়।

CLR & Threading 🔴 Senior / Lead (5-7+ Yrs)
১৪. ThreadPool Starvation কী? প্রোডাকশনে কীভাবে ডিবাগ করবেন এবং কেন এটি ক্যাটাস্ট্রফিক?

ThreadPool Starvation ঘটে যখন অ্যাসিনক্রোনাস কোডকে সিনক্রোনাসলি কল করা হয় (Sync-Over-Async যেমন task.Result বা task.Wait())। উচ্চ ট্রাফিকের সময় শত শত ইনকামিং রিকোয়েস্ট থ্রেডপুলের ওয়ার্কার থ্রেডগুলোকে ব্লক করে বসে থাকে।

ডটনেট থ্রেডপুল তাৎক্ষণিকভাবে থ্রেড তৈরি করতে পারে না; এটি Hill-Climbing Algorithm অনুযায়ী প্রতি সেকেন্ডে মাত্র ১-২টি থ্রেড বাড়াতে পারে। ফলে সার্ভারের সিপিইউ ইউসেজ মাত্র ৫%-১০% থাকা সত্ত্বেও সমস্ত ইনকামিং এপিআই কল কিউতে আটকে টাইমআউট (HTTP 503) হতে থাকে।

ডিবাগিং ও ফিক্স: প্রোডাকশনে dotnet-dump collect -p <PID> দিয়ে মেমোরি ডাম্প নিন। dotnet-dump analyze এ !threads কমান্ড দিলে দেখা যাবে শত শত থ্রেড Task.Wait বা Monitor.Wait-এ আটকে আছে। সমাধান: সম্পূর্ণ কোডবেস "Async All The Way" হতে হবে।

High Performance C# 🔴 Senior / Lead (5-7+ Yrs)
১৫. Span এবং Memory এর মধ্যে পার্থক্য কী? Span কেন async মেথডে ব্যবহার করা যায় না?

Span<T> হলো একটি ref struct যা মেমোরির যেকোনো কন্টিনিউয়াস ব্লকের (Stack, Heap, Native Unmanaged Memory) উপর একটি লাইটওয়েট উইন্ডো তৈরি করে কোনো মেমোরি এলোকেশন ও কপি ছাড়াই স্লাইসিং করতে দেয় (Zero Allocation)।

কেন async মেথডে Span ব্যবহার করা যায় না? টাইপ সেফটির কারণে CLR নিশ্চিত করে যে ref struct কখনো ম্যানেজড হিপে যেতে পারবে না—শুধুমাত্র স্ট্যাকে থাকবে। অ্যাসিনক্রোনাস মেথডে (async/await) মেথড সাসপেন্ড হওয়ার সময় স্টেট ধরে রাখার জন্য কম্পাইলার সমস্ত লোকাল ভ্যারিয়েবলকে হিপ মেমোরিতে একটি স্টেট মেশিন ক্লাসের ফিল্ডে রূপান্তর করে। যেহেতু হিপে ref struct রাখা অবৈধ, তাই কম্পাইলার await বাউন্ডারিতে Span<T> ব্যবহার করতে দেয় না। Memory<T> সাধারণ struct হওয়ায় হিপে থাকতে পারে এবং async মেথডে নিরাপদে পাস করা যায়।

CLR Internals 🔴 Senior / Lead (5-7+ Yrs)
১৬. .NET Garbage Collector Internals: Gen 0, 1, 2, LOH এবং POH এর মেকানিক্স ব্যাখ্যা করুন।

.NET GC হলো একটি Generational Tracing Garbage Collector:

  • Generation 0: স্বল্পস্থায়ী অবজেক্ট। কালেকশন অত্যন্ত দ্রুত (মাইক্রোসেকেন্ডে)। বেঁচে যাওয়া অবজেক্ট Gen 1 এ প্রমোট হয়।
  • Generation 1: বাফার জোন। Gen 0 এবং Gen 2 এর মধ্যে ট্রানজিশন স্তর।
  • Generation 2: দীর্ঘস্থায়ী অবজেক্ট (Singleton, Static Cache)। Gen 2 কালেকশনকে Full GC বলে, যা তুলনামূলক ব্যয়বহুল।
  • LOH (Large Object Heap): ৮৫,০০০ বাইট (৮৫ KB) বা তার বড় অবজেক্ট সরাসরি LOH-এ জমা হয়। এটি সাধারণত কম্প্যাক্ট করা হয় না, ফলে মেমোরি ফ্র্যাগমেন্টেশন হতে পারে।
  • POH (Pinned Object Heap): যে অবজেক্টগুলোকে মেমোরিতে নির্দিষ্ট ঠিকানায় পিন করে রাখতে হয় (Unmanaged ইন্টারপ বা সকেট I/O বাফার), সেগুলো এখানে থাকে যাতে অন্যান্য হিপ কম্প্যাক্ট হতে বাধা না পায়।

প্রোডাকশনে সর্বদা Server GC ব্যবহার করা হয়, যেখানে প্রতিটি CPU কোরের জন্য স্বাধীন হিপ ও থ্রেড থাকে।

ASP.NET Core Architecture 🔴 Senior / Lead (5-7+ Yrs)
১৭. Captive Dependency কী? কীভাবে এটি মেমোরি লিক ও কনকারেন্সি ক্র্যাশ তৈরি করে?

Captive Dependency ঘটে যখন দীর্ঘস্থায়ী কোনো সার্ভিস (যেমন: Singleton) তার ভেতর কম লাইফটাইমের কোনো সার্ভিসকে (যেমন: Scoped) কনস্ট্রাক্টরে ইনজেক্ট করে ধরে রাখে।

যেহেতু Singleton অ্যাপ্লিকেশন লাইফটাইমে একবার তৈরি হয়ে চিরকাল বেঁচে থাকে, তাই এর ভেতর ইনজেক্ট হওয়া Scoped সার্ভিসটিও (যেমন: DbContext) আর কখনো ডিসপোজ হতে পারে না—চিরকালের জন্য বন্দী হয়ে যায়।

ভয়ংকর পরিণতি: DbContext থ্রেড-সেফ নয়। একাধিক সমান্তরাল HTTP থ্রেড একই Singleton থেকে ক্যাপটিভ DbContext শেয়ার করায় InvalidOperationException এ সার্ভার ক্র্যাশ করে এবং অবজেক্ট রিলিজ না হওয়ায় মেমোরি লিক ঘটে। ফিক্স: ValidateScopes = true চালু রাখা।

High Performance & AOT 🔴 Senior / Lead (5-7+ Yrs)
১৮. ArrayPool এবং Native AOT এর বাস্তব সুবিধা ও চ্যালেঞ্জ কী কী?

ArrayPool<T>: উচ্চ ট্রাফিকের সময় প্রতি রিকোয়েস্টে বড় বাইট অ্যারে তৈরি না করে মেমোরি পুল থেকে ধার নেওয়া হয়: ArrayPool<byte>.Shared.Rent(4096)। কাজ শেষে Return(buffer) করলে বাফারটি পুনরায় ব্যবহারযোগ্য হয়। এটি Gen 2 ও LOH-এ নতুন অ্যালোকেশন ১০০% রোধ করে।

Tiered Compilation:

  • Tier 0 (Quick JIT): অ্যাপ স্টার্টআপ ফাস্ট করার জন্য কোনো অপ্টিমাইজেশন ছাড়াই অতি দ্রুত IL কোডকে মেশিন কোডে কম্পাইল করে।
  • Tier 1 (Optimized JIT): কোনো মেথড যদি প্রায় ৩০ বার কল হয়, CLR ব্যাকগ্রাউন্ড থ্রেডে সেই মেথডটিকে সর্বোচ্চ অপ্টিমাইজেশন দিয়ে পুনরায় কম্পাইল করে।
  • OSR (On-Stack Replacement): যদি কোনো দীর্ঘায়িত লুপ টিয়ার ০ মেথডের ভেতর চলতে থাকে, মেথড শেষ হওয়ার আগেই রানিং এক্সিকিউশনের মাঝপথেই কোডকে টিয়ার ১ অপ্টিমাইজড ভার্সনে হট-সোয়াপ করে দেয়।

২১. 64-bit CLR এ একটি Reference Object এর মেমোরি লেআউট কীরূপ? MethodTable Pointer ও SyncBlockIndex এর ভূমিকা কী?

একটি 64-bit সিস্টেমে হিপে তৈরি যেকোনো রেফারেন্স অবজেক্টের শুরুতে ১৬ বাইটের ওভারহেড (Object Header) থাকে:

[SyncBlockIndex (8 Bytes)] [MethodTable Pointer (8 Bytes)] [Object Fields / Data ...]
  1. SyncBlockIndex (8 বাইট): lock(obj) করার সময় মনিটর অবজেক্টের লক স্টেট, ডিফল্ট হ্যাশকোড (HashCode) এবং COM ইন্টারপ তথ্য ধারণ করে।
  2. MethodTable Pointer (8 বাইট): অবজেক্টটির টাইপ ডেসক্রিপ্টরকে নির্দেশ করে। ভার্চুয়াল মেথড ডিসপ্যাচ টেবিল (V-Table), ইন্টারফেস টেবিল এবং টাইপ মেটাডাটা এখানে থাকে।

মিনিমাম সাইজ ও প্যাডিং: 64-bit CLR এ একটি খালি অবজেক্টের সাইজও ন্যূনতম ২৪ বাইট (16 বাইট হেডার + 8 বাইট মিনিমাম অ্যালোকেশন অ্যালাইনমেন্ট)। ফিল্ডগুলো মেমোরিতে 8-বাইট বাউন্ডারিতে অ্যালাইন করা হয় (Memory Padding)।

Vector256<float> result = Vector256.Add(v1, v2);

৩৩. Conventional Middleware বনাম Factory-based (IMiddleware) এর মেমোরি ও লাইফটাইম পার্থক্য কী?

Conventional Middleware: RequestDelegate next কনস্ট্রাক্টরে নেয়। এটি অ্যাপ্লিকেশন স্টার্টআপের সময় একবার তৈরি হয় (কার্যত Singleton)। এর InvokeAsync(HttpContext context) মেথডে প্রতি রিকোয়েস্টে কোনো নতুন অবজেক্ট তৈরি হয় না (Zero Allocation)। তবে এর কনস্ট্রাক্টরে সরাসরি Scoped সার্ভিস ইনজেক্ট করলে Captive Dependency তৈরি হয়।

Factory-based (IMiddleware): IMiddleware ইন্টারফেস ইমপ্লিমেন্ট করে এবং IoC কন্টেইনারে AddTransient<MyMiddleware>() হিসেবে রেজিস্টার হয়। প্রতি রিকোয়েস্টে নতুন ইন্সট্যান্স তৈরি হয়, তাই কনস্ট্রাক্টরে নিরাপদে Scoped সার্ভিস (যেমন DbContext) ইনজেক্ট করা যায়। কিন্তু প্রতি রিকোয়েস্টে অবজেক্ট অ্যালোকেশন ওভারহেড থাকে।

৩৬. Clustered Index এবং Non-Clustered Index এর মূল পার্থক্য কী?

Clustered Index: টেবিলে ডেটার ফিজিক্যাল বিন্যাস সরাসরি নির্ধারণ করে। এর B-Tree স্ট্রাকচারের লিফ নোডে সম্পূর্ণ টেবিল ডেটা বা রো সংরক্ষিত থাকে। তাই একটি টেবিলে শুধুমাত্র একটিই Clustered Index থাকতে পারে (যেমন একটি ডিকশনারি বা টেলিফোন ডিরেক্টরি)। সাধারণত Primary Key-র উপর এটি স্বয়ংক্রিয়ভাবে তৈরি হয়।

Non-Clustered Index: মূল ডাটা টেবিল থেকে আলাদা একটি B-Tree স্ট্রাকচারে সংরক্ষিত থাকে। এর লিফ নোডে শুধুমাত্র ইনডেক্স করা কলামের ভ্যালু এবং মূল ডাটা রোর একটি পয়েন্টার (Row Locator / Clustered Key) থাকে। একটি টেবিলে একাধিক নন-ক্লাস্টার্ড ইনডেক্স থাকতে পারে (যেমন বইয়ের পেছনের ইনডেক্স সূচি)।

৩৭. Primary Key এবং Unique Key এর মধ্যে পার্থক্য কী? Foreign Key কীভাবে ডাটা ইন্টিগ্রিটি নিশ্চিত করে?

Primary Key: টেবিলের প্রতি রো-কে ইউনিকলি সনাক্ত করে। কখনোই NULL ভ্যালু অনুমোদন করে না। একটি টেবিলে শুধুমাত্র একটি প্রাইমারি কি থাকতে পারে এবং বাই-ডিফল্ট এটি Clustered Index তৈরি করে।

Unique Key: কলামের ভ্যালুর ইউনিকনেস নিশ্চিত করে কিন্তু NULL অনুমোদন করে। একটি টেবিলে একাধিক Unique Key থাকতে পারে এবং বাই-ডিফল্ট এটি Non-Clustered Index তৈরি করে।

Foreign Key: প্যারেন্ট ও চাইল্ড টেবিলের মধ্যে রিলেশনশিপ তৈরি করে। চাইল্ড টেবিলে এমন কোনো ভ্যালু ইনসার্ট হতে দেয় না যা প্যারেন্ট টেবিলে নেই। এটি রেফারেন্সিয়াল ইন্টিগ্রিটি বজায় রাখে।

SQL Joins দুটি টেবিলের সাধারণ কলামের ভিত্তিতে ডাটা একত্রিত করে:

  • INNER JOIN: উভয় টেবিলে ম্যাচিং হওয়া রেকর্ডগুলো শুধুমাত্র রিটার্ন করে।
  • LEFT JOIN: বাম টেবিলের সব রেকর্ড এবং ডান টেবিলের ম্যাচিং রেকর্ড আনে। ডানে ম্যাচ না থাকলে সেখানে NULL বসে।
  • RIGHT JOIN: ডান টেবিলের সব রেকর্ড এবং বামের ম্যাচিং রেকর্ড আনে।
  • FULL OUTER JOIN: যেকোনো এক টেবিলে মিল থাকলেই সব ডাটা নিয়ে আসে। অমিলের ক্ষেত্রে অপর পাশে NULL দেখায়।
  • CROSS JOIN: কার্টেসিয়ান গুণফল (Cartesian Product)। বাম টেবিলের প্রতিটি রো-র সাথে ডান টেবিলের প্রতিটি রো-কে জোড়া দেয় (M × N রো)।
Database Core 🟢 Junior (0-2 Yrs)
৩৯. ACID প্রোপার্টিজ কী? একটি ব্যাংক ফান্ড ট্রান্সফারের উদাহরণ দিয়ে বুঝিয়ে বলুন।

ACID হলো ডাটাবেজ ট্রানজ্যাকশনের ৪টি ভিত্তিস্তম্ভ:

  • Atomicity: অল অর নাথিং। রহিমের একাউন্ট থেকে ১০০০ টাকা কাটা এবং করিমের একাউন্টে জমা হওয়া—উভয়টি সম্পন্ন হতে হবে। মাঝে সার্ভার ক্র্যাশ করলে পুরো অপারেশন রোলব্যাক হবে।
  • Consistency: ট্রানজ্যাকশন শেষে সব ভ্যালিডেশন রুলস ও কনস্ট্রেইন্ট অক্ষত থাকবে। ব্যাংক ব্যালেন্স কখনো নেগেটিভ হতে পারবে না।
  • Isolation: সমান্তরাল ট্রানজ্যাকশন চললেও একটি অন্যটির অর্ধসমাপ্ত ডাটা রিড করতে পারে না।
  • Durability: একবার ট্রানজ্যাকশন COMMIT হয়ে গেলে বিদ্যুৎ চলে গেলেও ডাটা কখনো হারাবে না (Write-Ahead Logging এর মাধ্যমে)।
SQL DDL vs DML 🟢 Junior (0-2 Yrs)
৪০. DELETE, TRUNCATE এবং DROP এর মধ্যে প্রযুক্তিগত পার্থক্য কী?

DELETE (DML): WHERE ক্লজ দিয়ে নির্দিষ্ট রো মোছা যায়। রো-বাই-রো ট্রানজ্যাকশন লগে লেখে, তাই ধীরগতির। Identity মান রিসেট হয় না। ট্রিগার ফায়ার করে।

TRUNCATE (DDL): সমস্ত ডাটা পেজ তাৎক্ষণিকভাবে ডিঅ্যালোকেট করে। কোনো WHERE ক্লজ নেয় না। লগে কেবল পেজ ডিঅ্যালোকেশন লেখে, ফলে চোখের পলকে কোটি রো মুছে যায়। Identity রিসেট হয়। ট্রিগার ফায়ার করে না।

DROP (DDL): ডাটা সহ সম্পূর্ণ টেবিলের স্কিমা, স্ট্রাকচার ও ইনডেক্স ডাটাবেজ থেকে চিরতরে মুছে ফেলে।

Query Optimization 🟡 Mid-Level (2-5 Yrs)
৪১. Covering Index কী এবং INCLUDE ক্লজ কীভাবে Key Lookup দূর করে?

যখন কোনো কুয়েরির SELECT এর কিছু কলাম নন-ক্লাস্টার্ড ইনডেক্সে থাকে না, ইঞ্জিন ইনডেক্স খোঁজার পর বাকি কলাম আনতে মূল টেবিলে জাম্প করে—যাকে বলে Key Lookup (Bookmark Lookup)। উচ্চ ট্রাফিকে এটি সার্ভারের আই/ও ধ্বংস করে।

Covering Index: WHERE ক্লজের কলামকে ইনডেক্স কী-তে রেখে SELECT এর কলামগুলোকে INCLUDE ক্লজে দিলে সম্পূর্ণ কুয়েরি ইনডেক্স পেজ থেকেই সার্ভ হয়ে যায় এবং Key Lookup সম্পূর্ণরূপে ০ হয়ে যায়:

CREATE NONCLUSTERED INDEX IX_Orders_Cust 
ON Orders(CustomerId) 
INCLUDE (OrderDate, TotalAmount);
Execution Plan 🟡 Mid-Level (2-5 Yrs)
৪২. SQL Server Execution Plan এ Index Seek বনাম Index Scan এবং Hash Match এর তাৎপর্য কী?

Index Seek: B-Tree ইনডেক্সের রুট থেকে সরাসরি নির্দিষ্ট লিফ নোডে ঝাঁপ দেয়। এটি সবচেয়ে দ্রুত ও অপ্টিমাইজড (O(log N))।

Index Scan: সম্পূর্ণ ইনডেক্সের সমস্ত পেজ রিড করে। ইনডেক্সড কলামের উপর ফাংশন ব্যবহার করলে বা ফিল্টারিং মিস হলে এটি ঘটে।

Hash Match: দুটি বড় টেবিল জয়েন করতে ইঞ্জিন মেমোরিতে একটি ইন-মেমোরি হ্যাশ টেবিল তৈরি করে। এটি প্রচুর RAM এবং CPU খরচ করে। সঠিক ইনডেক্সিং থাকলে এটি দ্রুততর Merge Join বা Nested Loops-এ রূপান্তরিত হয়।

Database Modeling 🟡 Mid-Level (2-5 Yrs)
৪৩. ডাটাবেজ নরমালাইজেশন (1NF থেকে BCNF) বনাম ডিনরমালাইজেশন কখন প্রযোজ্য?

নরমালাইজেশন (OLTP): ডুপ্লিকেশন কমানো এবং Insert, Update, Delete এনোমালি রোধ করার প্রক্রিয়া। 1NF (অ্যাটমিক ভ্যালু), 2NF (পার্শিয়াল ডিপেনডেন্সি মুক্ত), 3NF (ট্রানজিটিভ ডিপেনডেন্সি মুক্ত)।

ডিনরমালাইজেশন (OLAP / High-Scale Read): যখন উচ্চ ট্রাফিকের কারণে জটিল ৭-৮টি টেবিল JOIN করা পারফরম্যান্সের জন্য ক্ষতিকর হয়ে দাঁড়ায়, তখন সচেতনভাবে কিছু রিডানড্যান্ট কলাম রেখে কুয়েরি দ্রুত করা হয়।

Concurrency & Deadlocks 🟡 Mid-Level (2-5 Yrs)
৪৫. SQL Server এ Deadlock কেন ঘটে? Deadlock Graph বিশ্লেষণ এবং প্রতিরোধের উপায় কী?

Deadlock: ঘটে যখন দুটি ট্রানজ্যাকশন একে অপরের দখল করা রিসোর্সের উপর এক্সক্লুসিভ লক দাবি করে একটি সাইক্লিক ডিপেনডেন্সিতে আটকে যায়। ইঞ্জিন একজনকে Deadlock Victim হিসেবে বেছে নিয়ে ১২০৫ এরর থ্রো করে।

প্রতিরোধ: ১. সমস্ত অ্যাপ্লিকেশনে টেবিল অ্যাক্সেসের ধারাবাহিকতা একই রাখা (Consistent Ordering)। ২. চাইল্ড টেবিলের Foreign Key কলামে ইনডেক্স নিশ্চিত করা। ৩. শর্ট ট্রানজ্যাকশন রাখা। ৪. RCSI সক্রিয় করা।

PostgreSQL Internals 🔴 Senior / Lead (5-7+ Yrs)
৪৬. PostgreSQL এ Table Bloat কেন ঘটে এবং Autovacuum কীভাবে টিউন করবেন?

Postgres এর MVCC ডিজাইনে কোনো রো আপডেট হলে ইঞ্জিন পুরনো রো এডিট করে না, বরং পুরনোটিকে Dead Tuple বানিয়ে নতুন রো ইনসার্ট করে। ঘনঘন আপডেটে কোটি কোটি ডেড টাপল ডিস্ক দখল করায় Table Bloat ঘটে এবং কুয়েরি স্লো হয়ে যায়।

VACUUM ডেড টাপল মুছে ডিস্ক স্পেস নতুন রো লেখার উপযোগী করে। হাই-রাইট টেবিলের জন্য autovacuum_vacuum_scale_factor = 0.05 (৫% ডেড টাপলেই ভ্যাকুয়াম চলবে) এবং HOT (Heap-Only Tuple) নিশ্চিত করতে fillfactor = 85 কনফিগার করা সিনিয়র বেস্ট প্র্যাকটিস।

Oracle Architecture 🔴 Senior / Lead (5-7+ Yrs)
৪৭. Oracle PL/SQL এ BULK COLLECT ও FORALL কেন লাখ লাখ রো প্রসেসিংয়ে গেম চেঞ্জার?

সাধারণ PL/SQL লুপে প্রতি রো প্রসেসিংয়ের সময় PL/SQL ইঞ্জিন ও SQL ইঞ্জিনের মধ্যে Context Switching ঘটে। ১০ লাখ রো-এর জন্য ১০ লাখ বার কনটেক্সট সুইচ হলে ঘণ্টার পর ঘণ্টা সময় অপচয় হয়।

BULK COLLECT ... LIMIT 1000 দিয়ে এক সিঙ্গেল রাউন্ডট্রিপে ১,০০০ রো মেমোরি অ্যারেতে আনা হয় এবং FORALL ... SAVE EXCEPTIONS দিয়ে এক ব্যাচে ডাটাবেজ ইঞ্জিনে পুশ করা হয়। এতে Context Switching সম্পূর্ণরূপে শূন্য হয়ে কোটি কোটি রো চোখের পলকে প্রসেস হয়।

SQL Server Deep Dive 🔴 Senior / Lead (5-7+ Yrs)
৪৮. Parameter Sniffing কী? প্রোডাকশনে কুয়েরি হঠাৎ স্লো হলে কীভাবে ফিক্স করবেন?

Parameter Sniffing: যখন কোনো Stored Procedure প্রথমবার রান হয়, SQL Server সেই নির্দিষ্ট প্যারামিটার ভ্যালুর জন্য সবচেয়ে অনুকূল একটি Execution Plan জেনারেট করে ক্যাশে রেখে দেয়। যদি প্রথম প্যারামিটারটি ছিল একটি ব্যতিক্রমী মান (Outlier, যা ১টি রো আনে), পরবর্তী সময়ে সাধারণ প্যারামিটার (যা লক্ষ রো আনবে) রান করলে ইঞ্জিন ওই পুরানো Index Seek প্ল্যান ব্যবহার করে হাজার হাজার Key Lookup করতে গিয়ে সিপিইউ ১০০% এ আটকে ফেলে।

ফিক্স: ১. লোকাল ভ্যারিয়েবল ট্রিক: DECLARE @LocalId INT = @ParamId; SELECT ... WHERE Id = @LocalId; ২. OPTION (OPTIMIZE FOR (@ParamId = 100)) ৩. OPTION (RECOMPILE)।

SQL Server Concurrency 🔴 Senior / Lead (5-7+ Yrs)
৪৯. Read Committed Snapshot Isolation (RCSI) কী এবং কেন এটি লক কনটেনশন বন্ধ করে?

ডিফল্ট SQL Server-এ রিড অপারেশনের সময় Shared Lock (S-Lock) লাগে। যদি কোনো ট্রানজ্যাকশন ডাটা আপডেট করতে থাকে (Exclusive X-Lock), রিডাররা ব্লক হয়ে বসে থাকে।

ALTER DATABASE MyDb SET READ_COMMITTED_SNAPSHOT ON; দিলে রিডাররা কোনো লক নেয় না। আপডেট চলাকালীন ইঞ্জিন পূর্বের কমিটেড ডাটার স্ন্যাপশট TempDB Version Store-এ রাখে। রিডাররা সরাসরি TempDB থেকে পূর্বের ভার্সন পড়ে চলে যায়। ফলে কোনো লকিং কনটেনশন থাকে না এবং কনকারেন্সি বহুগুণ বৃদ্ধি পায়।

Oracle Triggers 🔴 Senior / Lead (5-7+ Yrs)
৫০. Oracle এ Mutating Table Error (ORA-04091) কেন ঘটে এবং Compound Trigger দিয়ে কীভাবে সমাধান করবেন?

ORA-04091: যখন একটি AFTER INSERT OR UPDATE FOR EACH ROW ট্রিগারের ভেতর থেকে সেই একই টেবিলের উপর SELECT কুয়েরি চালানো হয় যা বর্তমানে ট্রানজ্যাকশনের অধীনে মডিফাই হচ্ছে। ডাটাবেজ তখন টেবিলটিকে Mutating ঘোষণা করে এরর দেয়।

Compound Trigger এর সমাধান: এটি ৪টি ফেজে কাজ করে: ১. BEFORE STATEMENT (অ্যারে ইনিশিয়ালাইজ), ২. AFTER EACH ROW (কোনো কুয়েরি না চালিয়ে শুধুমাত্র আইডিগুলো অ্যারেতে পুশ), ৩. AFTER STATEMENT (টেবিলের লক মুক্ত হওয়ার পর অ্যারেতে থাকা আইডিগুলোর উপর একবার বাল্ক কুয়েরি চালিয়ে রুলস প্রয়োগ)।

Redis Distributed Caching 🔴 Senior / Lead (5-7+ Yrs)
৫১. Redis Caching: Cache Stampede (Dogpiling) কী? XFetch ও RedLock কীভাবে কাজ করে?

Cache Stampede: যখন হট কি-র ক্যাশ এক্সপায়ার হয়, হাজার হাজার কনকারেন্ট রিকোয়েস্ট ক্যাশে ডাটা না পেয়ে একসাথে ডাটাবেজে আঘাত হানে এবং ডাটাবেজ ক্র্যাশ করে।

সমাধান: ১. XFetch Algorithm (Probabilistic Early Expiration): ক্যাশ এক্সপায়ার হওয়ার সামান্য আগে গাণিতিক সম্ভাবনার ভিত্তিতে একটি মাত্র ব্যাকগ্রাউন্ড থ্রেড ডাটাবেজ থেকে ক্যাশ রিফ্রেশ করে নেয়। ২. Distributed Mutex (RedLock): প্রথম রিকোয়েস্টটি লক নিয়ে ডাটাবেজ পড়বে, বাকি রিকোয়েস্টগুলো অপেক্ষা করে নতুন ক্যাশ থেকে ডাটা পাবে।

SQL Storage Internals 🔴 Senior / Lead (5-7+ Yrs)
৫২. SQL Server Data Page Lifecycle: 8KB Page, Extent (Uniform vs Mixed), Page Split এবং PFS/GAM/SGAM পেজ কী?

SQL Server মেমোরি ও ডিস্কে ডেটা সংরক্ষণ করে 8KB (৮,১৯২ বাইট) Data Page আকারে। ৮টি কন্টিনিউয়াস পেজ নিয়ে গঠিত হয় একটি 64KB Extent।

  • Uniform Extent: সমস্ত ৮টি পেজ একটি একক টেবিল বা অবজেক্টের মালিকানাধীন।
  • Mixed Extent: ৮টি পেজ বিভিন্ন টেবিল শেয়ার করে (ছোট টেবিলের অপচয় রোধে)।
  • Bad Page Split: যখন একটি ইন্ডেক্স পেজ ৯৯% পূর্ণ থাকে এবং তার মাঝে একটি নতুন রো ইনসার্ট করতে হয়, ইঞ্জিন তাৎক্ষণিকভাবে একটি নতুন পেজ অ্যালোকেট করে অর্ধেক রো সেখানে সরিয়ে নেয় (৫০-৫০ স্প্লিট)। এটি ভারী ডিস্ক আই/ও এবং সূচক ফ্র্যাগমেন্টেশন (Fragmentation) তৈরি করে।
  • অ্যালোকেশন ট্র্যাকিং পেজ: GAM (Global Allocation Map) ফ্রি এক্সটেন্ট ট্র্যাক করে, SGAM শেয়ার্ড এক্সটেন্ট ট্র্যাক করে, এবং PFS (Page Free Space) প্রতিটি পেজের ভেতর কত পারসেন্ট ফ্রি স্পেস আছে তা বাইট আকারে ট্র্যাক করে।
Query Optimizer Internals 🔴 Senior / Lead (5-7+ Yrs)
৫৩. Cardinality Estimation এবং SQL Statistics: Histogram, Density Vector এবং CE2014+ এর পরিবর্তন কী?

কুয়েরি অপ্টিমাইজার কোনো এক্সিকিউশন প্ল্যান তৈরির আগে দেখে টেবিলের ফিল্টারে কতগুলো রো ম্যাচ করতে পারে—যাকে বলে Cardinality Estimation (CE)। এর ভিত্তি হলো Statistics।

  • Histogram: সর্বোচ্চ ২০০টি স্টেপ (Buckets) এ ডাটার বন্টন, রেঞ্জ এবং ফ্রিকোয়েন্সি রেকর্ড করে।
  • Density Vector: একাধিক কলামের ইউনিকনেসের পরিমাপ (1 / Distinct Values)। ইনডেক্স কলামের সমন্বয়ে কত পারসেন্ট ডুপ্লিকেশন আছে তা বোঝায়।
  • CE2014+ পরিবর্তন: SQL Server 2014-এর নতুন CE ইঞ্জিন স্বাধীন কলাম অনুমানের বদলে Exponential Backoff Model (কলাম ১ ১০০%, কলাম ২ ৩০%, কলাম ৩ ৯%) ব্যবহার করে। জটিল মাল্টি-কলাম প্রেডিকেটে যদি পুরানো CE ভালো কাজ করে, তবে USE HINT ('FORCE_LEGACY_CARDINALITY_ESTIMATION') দিয়ে পুরানো মডেলে ফোর্স করা যায়।
Advanced Locking 🔴 Senior / Lead (5-7+ Yrs)
৫৪. Lock Escalation কী? Row-level Lock কখন Table Lock এ রূপান্তর হয় এবং কীভাবে ঠেকাবেন?

প্রতিটি লকের জন্য মেমোরিতে প্রায় ৯৬ বাইট খরচ হয়। মেমোরি বাঁচাতে যখন একটি একক ট্রানজ্যাকশন একটি একক টেবিলে ৫,০০০ এর বেশি রো বা পেজ লক অর্জন করে, SQL Server স্বয়ংক্রিয়ভাবে সমস্ত রো লককে একটি একক Exclusive Table Lock (X-Table Lock) এ রূপান্তর করে দেয়—যাকে বলে Lock Escalation।

ভয়ংকর পরিণতি: টেবিল লক হয়ে যাওয়ায় অন্য সমস্ত ব্যবহারকারীর রিড/রাইট সম্পূর্ণ ব্লক হয়ে যায়।

প্রতিরোধ:

  1. লাখ লাখ রো একবারে আপডেট না করে ব্যাচ আকারে (Chunks of 2,000 rows) আপডেট করুন।
  2. টেবিলে পার্টিশনিং থাকলে পার্টিশন-লেভেল লকিং অন করুন: ALTER TABLE Orders SET (LOCK_ESCALATION = AUTO); (শুধুমাত্র অ্যাফেক্টেড পার্টিশন লক হবে, পুরো টেবিল নয়)।
Partitioning & Archiving 🔴 Senior / Lead (5-7+ Yrs)
৫৫. Table Partitioning এ Sliding Window Pattern এবং SWITCH PARTITION কীভাবে বিলিয়ন রো জিরো-লগে আর্কাইভ করে?

Sliding Window Pattern: টাইম-সিরিজ ডেটাবেজে (যেমন ১০ কোটি অডিট লগ) প্রতি মাসের জন্য আলাদা পার্টিশন তৈরি করা হয় (Partition Function & Scheme)।

SWITCH PARTITION এর ম্যাজিক:

ALTER TABLE ActiveAuditLogs SWITCH PARTITION 1 TO ArchivedAuditLogs;

এটি কোনো ডাটা ফিজিক্যালি মুভ বা কপি করে না, কোনো ট্রানজ্যাকশন লগ জেনারেট করে না। এটি কার্নেল মেটাডাটা পয়েন্টার পরিবর্তন করে এক নিমিষে (১ মিলি-সেকেন্ডে) কোটি কোটি রো একটি টেবিল থেকে অন্য টেবিলে স্থানান্তর করে দেয়। ফলে প্রোডাকশনে ডেটা আর্কাভিঙে কোনো সার্ভার ল্যাগ বা লক হয় না।

৫৬. In-Memory OLTP (Hekaton): Memory-Optimized Tables এবং Natively Compiled Stored Procedures কেন ২০ গুণ দ্রুত?

SQL Server In-Memory OLTP সম্পূর্ণ মেমোরিতে অপ্টিমাইজড Bw-Tree এবং হ্যাশ ইনডেক্স ব্যবহার করে।

  • Latch-Free & Lock-Free: সাধারণ ডাটাবেজের মতো কোনো লকিং মেকানিজম নেই। এটি মাল্টি-ভার্সন অপটিমিস্টিক কনকারেন্সিতে কাজ করে, ফলে কোনো থ্রেড কাউকে ব্লক করে না।
  • Natively Compiled Stored Procedures: T-SQL কোডকে ইন্টারপ্রেট না করে সরাসরি সি (C) ল্যাঙ্গুয়েজের মেশিন কোড DLL-এ কম্পাইল করে রানটামে এক্সিকিউট করে। ফলে ইন্টারপ্রিটেশন ওভারহেড শূন্য হয়ে যায় এবং সাধারণ কুয়েরির চেয়ে ২০ থেকে ৩০ গুণ বেশি থ্রুপুট দেয়।
Temporal Data & Audit 🔴 Senior / Lead (5-7+ Yrs)
৫৭. Temporal Tables (System-Versioned Tables) কীভাবে স্বয়ংক্রিয় অডিট এবং Point-in-Time ট্রাভেল সমর্থন করে?

SQL Server 2016+ এ SYSTEM_VERSIONING = ON দিয়ে Temporal Table ডিক্লেয়ার করা যায়:

CREATE TABLE Employee (
    EmpId INT PRIMARY KEY, Name VARCHAR(100),
    SysStartTime DATETIME2 GENERATED ALWAYS AS ROW START,
    SysEndTime DATETIME2 GENERATED ALWAYS AS ROW END,
    PERIOD FOR SYSTEM_TIME (SysStartTime, SysEndTime)
) WITH (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.EmployeeHistory));

কোনো রো আপডেট বা ডিলিট হলে ইঞ্জিন নিজে থেকেই পুরানো স্ন্যাপশটটি হিস্ট্রি টেবিলে টাইমস্ট্যাম্প সহ আর্কাইভ করে। অ্যাপ্লিকেশন কোনো অডিট ট্রিগার বা কোড ছাড়াই সরাসরি Time Travel Query করতে পারে:

SELECT * FROM Employee FOR SYSTEM_TIME AS OF '2024-01-01 12:00:00';
PostgreSQL Deep Engine 🔴 Senior / Lead (5-7+ Yrs)
৫৮. PostgreSQL Internals: FSM (Free Space Map), VM (Visibility Map), HOT Updates এবং WAL Write Amplification?

Free Space Map (FSM): প্রতিটি টেবিল ফাইলের সাথে একটি _fsm ফাইল থাকে যা বাইনারি ট্রিতে ট্র্যাক করে কোন পেজে নতুন রো ইনসার্ট করার মতো পর্যাপ্ত ফ্রি স্পেস আছে।

Visibility Map (VM): ট্র্যাক করে কোন পেজের সমস্ত টাপল সমস্ত অ্যাক্টিভ ট্রানজ্যাকশনের কাছে দৃশ্যমান। এটি থাকলে ইঞ্জিন সরাসরি Index-Only Scan করতে পারে—হিপ পেজ রিড করার প্রয়োজনই হয় না।

HOT (Heap-Only Tuple) Update: যদি আপডেটে কোনো ইনডেক্সড কলাম পরিবর্তন না হয় এবং একই পেজে পর্যাপ্ত জায়গা থাকে, Postgres কোনো নতুন ইনডেক্স এন্ট্রি তৈরি না করেই পেজের ভেতর পয়েন্টার চেইন করে। এটি ৯৯% ডিস্ক আই/ও বাঁচিয়ে দেয়।

৫৯. PostgreSQL Index Types: B-tree বনাম GIN বনাম GiST বনাম BRIN কখন কোনটি বেছে নেবেন?
ইনডেক্স টাইপআন্ডারলাইং স্ট্রাকচারআদর্শ ব্যবহার ক্ষেত্র
B-treeব্যালেন্সড ট্রিসাধারণ ইউনিক মান, সমতা (=) এবং রেঞ্জ (<, >) কুয়েরি।
GIN (Generalized Inverted Index)ইনভার্টেড ইনডেক্সJSONB ডকুমেন্টস, টেক্সট সার্চ (Full-text Search), এবং Array এলিমেন্ট অনুসন্ধান।

BRIN (Block Range Index)ব্লক রেঞ্জ মেটাডাটাবিলিয়ন রো-র বিশাল টাইম-সিরিজ টেবিল যেখানে ডেটা শারীরিকভাবে সর্টেড থাকে। ইনডেক্স সাইজ B-Tree এর তুলনায় ১% মাত্র!
Connection Pooling PgBouncer 🔴 Senior / Lead (5-7+ Yrs)
৬০. PgBouncer Connection Pooling: Session বনাম Transaction বনাম Statement মোড এবং Prepared Statements সমস্যা?

Postgres প্রতি ক্লায়েন্ট কানেকশনে একটি সম্পূর্ণ ওএস প্রসেস (Fork) তৈরি করে যাতে ১০ MB মেমোরি খরচ হয়। তাই সামনে PgBouncer ব্যবহার করা বাধ্যতামূলক।

  • Session Pooling: ক্লায়েন্ট ডিসকানেক্ট না হওয়া পর্যন্ত পুরো ডাটাবেজ কানেকশন ধরে রাখে (কম স্কেলেবল)।
  • Transaction Pooling (সর্বোচ্চ স্কেলেবল): শুধুমাত্র ট্রানজ্যাকশন চলার সময় পুল থেকে কানেকশন ধার নেয় এবং COMMIT হওয়া মাত্র কানেকশন অন্য রিকোয়েস্টকে দিয়ে দেয়।
  • Prepared Statement সমস্যা ও সমাধান: Transaction মোডে পরবর্তী কুয়েরি ভিন্ন ব্যাকএন্ড প্রসেসে যেতে পারে, তাই সার্ভার-সাইড প্রিপেয়ার্ড স্টেটমেন্ট ফেইল করে। .NET Npgsql ড্রাইভারের জন্য কানেকশন স্ট্রিংয়ে Max Auto Prepare=0 অথবা PgBouncer 1.21+ এর প্রিপেয়ার্ড স্টেটমেন্ট সাপোর্ট কনফিগার করতে হয়।
Oracle Optimizer & Plans 🔴 Senior / Lead (5-7+ Yrs)
৬১. Oracle Cost-Based Optimizer (CBO): Adaptive Cursor Sharing এবং SQL Plan Baselines কীভাবে কুয়েরি স্ট্যাবিলিটি নিশ্চিত করে?

Adaptive Cursor Sharing (ACS): প্যারামিটারযুক্ত কুয়েরিতে যদি ডেটা স্কিউড (Skewed) থাকে, Oracle CBO রানটাইমে মনিটর করে কুয়েরির বাফার গেটস। প্রয়োজন অনুযায়ী সে একাধিক এক্সিকিউশন প্ল্যান তৈরি করে ভিন্ন ভিন্ন প্যারামিটারের জন্য সঠিক প্ল্যান বেছে নেয়।

SQL Plan Baselines (SPM): প্রোডাকশনে ডাটাবেজ আপগ্রেড বা অপটিমাইজার পরিবর্তনের সময় কোনো কুয়েরি যাতে হঠাৎ খারাপ প্ল্যানে চলে না যায়, তার জন্য DBMS_SPM দিয়ে সুনির্দিষ্ট প্ল্যান বেসলাইন লক করে দেওয়া হয়। নতুন প্ল্যান ভেরিফাই ও টেস্টেড না হওয়া পর্যন্ত অপটিমাইজার তা গ্রহণ করে না।

৬২. Oracle Flashback Query (AS OF TIMESTAMP) এবং Flashback Drop দিয়ে ডেটা করাপশন থেকে তাৎক্ষণিক রিকভারি?

যদি কোনো ডেভেলপার অসাবধানতাবশত প্রোডাকশনে DELETE FROM Customers (WHERE ক্লজ ছাড়া) চালিয়ে দেয়:

১. Flashback Query: ব্যাকআপ রিস্টোর করার কোনো প্রয়োজন নেই। Undo Tablespace ব্যবহার করে ১০ মিনিট আগের সঠিক ডেটা পড়ে ফিরিয়ে আনা যায়:

INSERT INTO Customers SELECT * FROM Customers AS OF TIMESTAMP (SYSTIMESTAMP - INTERVAL '15' MINUTE);

২. Flashback Drop: ভুলবশত টেবিল ড্রপ করা হলে Oracle তা সরাসরি ডিলিট না করে Recyclebin-এ রাখে: FLASHBACK TABLE Customers TO BEFORE DROP; কমান্ড দিলে টেবিলের সমস্ত ডাটা ও ইনডেক্স চোখের পলকে রিস্টোর হয়।

৬৩. Redis Memory Management: 8টি Eviction Policies এর পার্থক্য কী এবং ক্যাশে কোনটি সেরা?

  • noeviction (ফাইন্যান্সিয়ালের জন্য): কোনো কি ডিলিট করবে না, নতুন রাইট এলে OOM command not allowed এরর ফেরত দেবে।
Redis Persistence Internals 🔴 Senior / Lead (5-7+ Yrs)
৬৪. Redis Persistence: RDB Snapshotting বনাম AOF (Append-Only File) এর মেকানিক্স এবং Hybrid Persistence?

RDB (Redis Database Snapshot): নির্দিষ্ট বিরতিতে (যেমন ১৫ মিনিটে) মেমোরির একটি কমপ্যাক্ট বাইনারি স্ন্যাপশট ডিস্কে dump.rdb ফাইলে সেভ করে (OS Fork মেকানিজম দিয়ে)। এটি ফাস্ট রিস্টার্ট দেয় কিন্তু ক্র্যাশ করলে শেষ কয়েক মিনিটের ডেটা নষ্ট হতে পারে।

AOF (Append-Only File): প্রতিটি রাইট কমান্ড একটি টেক্সট লগে অ্যাপেন্ড করে। fsync everysec মোডে ডেটা হারানোর ঝুঁকি সর্বোচ্চ ১ সেকেন্ড। তবে ফাইল সাইজ অনেক বড় হয়।

Hybrid Persistence (Redis 4.0+ ডিফল্ট): AOF রিরাইটের সময় ফাইলের শুরুতে কমপ্যাক্ট RDB স্ন্যাপশট লেখে এবং বাকি অংশে রানিং ট্রানজ্যাকশনের ডেল্টা AOF লগ রাখে। এটি দ্রুততম রিস্টার্ট এবং শূন্য ডেটা লসের নিখুঁত সমন্বয়।

High Availability Redis 🔴 Senior / Lead (5-7+ Yrs)
৬৫. Redis Sentinel বনাম Redis Cluster: Split-Brain ফল্ট এবং min-replicas-to-write সুরক্ষাবলয় কী?

Redis Sentinel: হাই-অ্যাভেইলেবিলিটি (Failover) নিশ্চিত করে। মাস্টার ক্র্যাশ করলে সেন্টিনেল কোরাম (Quorum) ভোটের মাধ্যমে নতুন রেপলিকাকে মাস্টার বানায়।

Split-Brain ঝুঁকি: নেটওয়ার্ক পার্টিশনের কারণে পুরানো মাস্টার আইসোলেটেড হয়ে গেলেও ক্লায়েন্টের কাছ থেকে রাইট নিতে থাকে, আর অপর পাশে সেন্টিনেল নতুন মাস্টার বানিয়ে ফেলে। নেটওয়ার্ক ঠিক হলে পুরানো মাস্টারের সমস্ত ডাটা স্থায়ীভাবে ডিলিট হয়ে যায়।

প্রতিরোধ:

min-replicas-to-write 1
min-replicas-max-lag 10

এটি নিশ্চিত করে যদি মাস্টার অন্তত ১টি সুস্থ রেপলিকাকে ১০ সেকেন্ডের ভেতর পিং না পায়, তবে সে নিজে থেকেই ক্লায়েন্টের নতুন রাইট রিকোয়েস্ট রিজেক্ট করে দেবে এবং ডেটা ইনকনসিস্টেন্সি রোধ করবে।

Advanced Redis Structures 🔴 Senior / Lead (5-7+ Yrs)
৬৬. Redis Sorted Sets (ZSET with SkipList) এবং HyperLogLog দিয়ে কোটি কোটি ইউজারের লিডারবোর্ড ও ইউনিক ভিজিটর কাউন্ট?

Sorted Sets (ZSET): প্রতিটি এলিমেন্টের সাথে একটি স্কোর থাকে। ইন্টারনালি এটি SkipList + Hash Table দিয়ে তৈরি, যা O(log N) সময়ে ইনসার্ট এবং রেঞ্জ কোয়েরি চালায়। কোটি খেলোয়াড়ের লাইভ গেম লিডারবোর্ড বা টপ র্যাঙ্কিং পেজিং (ZREVRANGEBYSCORE) চোখের পলকে সার্ভ করে।

HyperLogLog: একটি ওয়েবসাইটে দৈনিক কোটি কোটি ইউনিক ভিজিটর (Cardinality) কাউন্ট করতে যদি সেট (Set) ব্যবহার করা হয়, গিগাবাইট মেমোরি খরচ হবে। PFADD এবং PFCOUNT ব্যবহার করে HyperLogLog মাত্র ১২ KB মেমোরিতে ৯৯.১9% নিখুঁত সম্ভাব্যতায় কোটি কোটি ইউনিক ভিজিটর গণনা করতে পারে!

High Availability AlwaysOn 🔴 Senior / Lead (5-7+ Yrs)
৬৮. SQL Server AlwaysOn Availability Groups: Synchronous বনাম Asynchronous Commit এবং Read-Only Routing?

AlwaysOn এ একটি প্রাইমারি ডাটাবেজের ট্রানজ্যাকশন লগ এক বা একাধিক সেকেন্ডারি নোডে রেপ্লিকেট হয়:

  • Synchronous-Commit: সেকেন্ডারি নোডে লগ হার্ডেন (DiskWriten) না হওয়া পর্যন্ত প্রাইমারিতে ট্রানজ্যাকশন COMMIT সম্পন্ন হয় না (Zero Data Loss - RPO = 0)। কিন্তু নেটওয়ার্ক ল্যাটেন্সির কারণে রাইট কিছুটা স্লো হতে পারে।
  • Asynchronous-Commit: প্রাইমারি নিজে কমিট করে সেকেন্ডারিতে ব্যাকগ্রাউন্ডে পাঠায়। হাই পারফরম্যান্স দেয় কিন্তু নোড ক্র্যাশ করলে সামান্য ডেটা লস হতে পারে (Disaster Recovery সাইটের জন্য সেরা)।
  • Read-Only Routing: সেকেন্ডারি নোডগুলোকে রিড-অনলি হিসেবে কনফিগার করে সংযোগ স্ট্রিংয়ে ApplicationIntent=ReadOnly দিলে সমস্ত ভারি রিপোর্টিং কুয়েরি স্বয়ংক্রিয়ভাবে সেকেন্ডারিতে চলে যায়, ফলে প্রাইমারি নোড ১০০% ফ্রি থাকে।
Concurrency Conflicts 🔴 Senior / Lead (5-7+ Yrs)
৬৯. Optimistic Concurrency Control (RowVersion / Timestamp in EF Core) বনাম Pessimistic Concurrency (UPDLOCK)?

Optimistic Concurrency (উচ্চ ট্রাফিকের স্ট্যান্ডার্ড): টেবিলে একটি RowVersion (byte[]) কলাম রাখা হয়। ডাটাবেজে লক না নিয়ে ডাটা পড়া হয়। সেভ করার সময় UPDATE ... WHERE Id = @Id AND RowVersion = @OriginalVersion চেক করা হয়। যদি অন্য কোনো ব্যবহারকারী মাঝপথে আপডেট করে ফেলে, DbUpdateConcurrencyException থ্রো হয় যা ক্যাচ করে ইউজারকে কনফ্লিক্ট নোটিফাই করা যায়।

Pessimistic Concurrency: কুয়েরির সময়ই ডেটাতে এক্সক্লুসিভ লক (WITH (UPDLOCK, HOLDLOCK)) নেওয়া হয় যাতে ট্রানজ্যাকশন শেষ না হওয়া পর্যন্ত আর কেউ ডাটা পড়তে বা এডিট করতে না পারে। টিকিট বুকিং বা এটিএম ব্যালেন্স কাটার মতো সেনসিটিভ ক্রাইটেরিয়ায় এটি প্রযোজ্য।

৭০. SARGability (Search Argument Able) কী? Non-SARGable কুয়েরি কীভাবে ইনডেক্স অকেজো করে এবং কীভাবে ফিক্স করবেন?

SARGable: একটি কুয়েরি তখন SARGable হয় যখন ডাটাবেজ ইঞ্জিন সরাসরি B-Tree ইনডেক্সে Index Seek অপারেশন চালাতে পারে।

Non-SARGable এর সাধারণ পাপসমূহ:

  1. কলামের উপর ফাংশন ব্যবহার: WHERE YEAR(CreatedDate) = 2024 → ইঞ্জিন বাধ্য হয়ে সম্পূর্ণ কোটি রো স্ক্যান (Index Scan) করবে।

  3. ইমপ্লিসিট ডাটা টাইপ কনভার্সন: কলাম VARCHAR অথচ প্যারামিটার পাস করা হলো NVARCHAR। ইঞ্জিন প্রতি রো-তে কনভার্সন ফাংশন বসিয়ে ইনডেক্স অকেজো করে ফেলে।

CSS Grid (২-মাত্রিক Layout): একই সাথে সারি ও কলাম (Rows এবং Columns) উভয় অক্ষ সম্পূর্ণ নিয়ন্ত্রণ করে। লেআউট চালিত ডিজাইন (Layout-first)। পুরো পেজের কাঠামো, জটিল ড্যাশবোর্ড এবং রেসপনসিভ ফটো গ্যালারির জন্য সেরা।

সিদ্ধান্ত: পুরো পেজের ম্যাক্রো কাঠামো গ্রিড দিয়ে এবং কম্পোনেন্টের ভেতরের মাইক্রো অ্যালাইনমেন্ট ফ্লেক্সবক্স দিয়ে সাজানো সেরা আর্কিটেকচার।

৭৫. Angular Component Lifecycle Hooks এর প্রধান ধাপগুলো কী কী? ngOnInit বনাম Constructor?

Constructor: সাধারণ TypeScript ক্লাসের ফিচার। শুধুমাত্র ডিপেনডেন্সি ইনজেকশন করার জন্য ব্যবহৃত হয়। এই ধাপে ইনপুট প্রোপার্টিজ (@Input) মান পায় না এবং DOM তৈরি হয় না।

প্রধান লাইফসাইকেল হুকস:

  1. ngOnChanges(): যখন কোনো @Input() প্রোপার্টির মান পরিবর্তিত হয়।
  2. ngOnInit(): কম্পোনেন্ট ইনিশিয়ালাইজ হলে একবার কল হয়। প্রাথমিক ডাটা ও এপিআই কল এখানে করা হয়।
  3. ngAfterViewInit(): কম্পোনেন্টের টেমপ্লেট ও চাইল্ড ভিউ পুরোপুরি DOM এ রেন্ডার হওয়ার পর কল হয়।
  4. ngOnDestroy(): কম্পোনেন্ট ডোম থেকে অপসারিত হওয়ার ঠিক আগে কল হয়। মেমোরি লিক রোধ করতে সমস্ত সাবস্ক্রিপশন আনসাবস্ক্রাইব করার স্থান।

৭৬. jQuery Event Delegation কী? $('.item').click() এর বদলে $(document).on('click', '.item') কেন শ্রেয়?

Container Queries (@container): উইজেটটির প্যারেন্ট কন্টেইনারের প্রস্থ বা আকারের উপর ভিত্তি করে রেসপনসিভ স্টাইল দেয়। ফলে একটি কার্ড কম্পোনেন্টকে আপনি সাইডবারে রাখলে নিজে থেকেই কমপ্যাক্ট কলামে চলে আসবে, আবার মেইন সেকশনে রাখলে নিজে থেকেই গ্রিড হয়ে যাবে—সম্পূর্ণ স্বাধীন ও পুনঃব্যবহারযোগ্য কম্পোনেন্ট ডিজাইন সম্ভব হয়।

৭৯. Angular Hierarchical Dependency Injection কীভাবে কাজ করে? providedIn: 'root' বনাম Component Providers?

  1. providedIn: 'root' (Root Injector): পুরো অ্যাপ্লিকেশনে একটি মাত্র Singleton ইন্সট্যান্স তৈরি হয় এবং ট্রি-শেকিং (Tree-shaking) সমর্থন করে। অব্যবহৃত সার্ভিস প্রোডাকশন বান্ডেলে বাদ পড়ে।
  2. Component providers: [MyService]: সেই কম্পোনেন্ট এবং তার চাইল্ড কম্পোনেন্টের জন্য একটি লোকাল আইসোলেটেড ইন্সট্যান্স তৈরি হয়। কম্পোনেন্ট নষ্ট হলে সার্ভিসটিও ডিসপোজ হয়। এটি মাল্টি-ইনস্ট্যান্স উইজেটের নিজস্ব স্টেটের জন্য উপযোগী।

৮০. RxJS Flattening Operators: switchMap, mergeMap, concatMap এবং exhaustMap এর সুনির্দিষ্ট ব্যবহার ক্ষেত্র কী?

উচ্চ কনকারেন্সির সময় এই ৪টি অপারেটরের পার্থক্য জেনে রাখা জরুরি:

  • switchMap: নতুন ইভেন্ট আসা মাত্র আগের পেন্ডিং সাবস্ক্রিপশন বাতিল (Cancel) করে। ব্যবহার: সার্চ অটো-সাজেস্ট টাইপিং।
  • mergeMap: সমস্ত ইনকামিং ইভেন্টকে সমান্তরালভাবে (Parallel) হ্যান্ডেল করে। ব্যবহার: প্যারালাল মাল্টি-ফাইল আপলোড।
  • concatMap: আগের অপারেশন শেষ না হওয়া পর্যন্ত পরেরটি কিউতে রাখে (Sequential Queue)। ব্যবহার: অ্যাকাউন্ট ডেবিট বা চ্যাট মেসেজ সিকোয়েন্স।
  • exhaustMap: আগের কাজ শেষ না হওয়া পর্যন্ত পরবর্তী সমস্ত ইনকামিং ইভেন্ট ড্রপ করে। ব্যবহার: ফর্ম সাবমিট বা পেমেন্ট বাটনে বারবার ডাবল ক্লিক প্রতিরোধ।

৮১. Angular 18 এ Signals বনাম RxJS এর সুনির্দিষ্ট আর্কিটেকচারাল ব্যবহার ক্ষেত্র কী?

Angular Signals: সিঙ্ক্রোনাস রিঅ্যাক্টিভ স্টেট (Synchronous State)। কম্পোনেন্টের লোকাল স্টেট, ডোম প্রোপার্টিজ ও ক্যালকুলেটেড ডেরিভেশনের জন্য সেরা। কোনো মেমোরি লিক রিস্ক নেই এবং ম্যানুয়াল আনসাবস্ক্রাইব করার প্রয়োজন হয় না। এটি ভবিষ্যতে Zone.js মুক্ত লাইটওয়েট অ্যাঙ্গুলার সম্ভব করছে।

RxJS Observables: অ্যাসিনক্রোনাস ইভেন্ট স্ট্রিম (Asynchronous Streams)। HTTP রিকোয়েস্ট, সার্চ ইনপুটে Debouncing, WebSockets এবং জটিল টাইমিং অর্কেস্ট্রেশনে RxJS অপরিহার্য। আধুনিক অ্যাঙ্গুলারে两者 মিলে কাজ করে (toSignal এবং toObservable ইন্টারঅপারেবিলিটি)।

৮৩. Angular Control Flow (@if, @for track) এবং @defer এর পারফরম্যান্স বেনিফিট কী?

Modern Control Flow: নতুন @if এবং @for (item of items; track item.id) কম্পাইলার লেভেলে অপ্টিমাইজড। track ক্লজ বাধ্যতামূলক করায় রি-রেন্ডারিংয়ে ডোম ম্যানিপুলেশন ৯০% কমে যায়।

৯১. V8 Engine Internals: Hidden Classes, Inline Caches (Monomorphic vs Megamorphic) এবং Event Loop এর Microtasks?

Hidden Classes: জাভাস্ক্রিপ্টে ক্লাস না থাকলেও V8 ইন্টারনালি মেমোরিতে প্রতিটি অবজেক্টের জন্য একটি হিডেন ক্লাস তৈরি করে। কনস্ট্রাক্টরের বাইরে ডায়নামিকালি প্রোপার্টি যোগ করলে (obj.newProp = 1) হিডেন ক্লাস পরিবর্তিত হয় এবং মেমোরি লুকআপ স্লো হয়ে যায়।

Inline Cache (IC): মেথড কল অপ্টিমাইজ করে। যদি একটি ফাংশন সর্বদা একই হিডেন ক্লাসের অবজেক্ট পায়, তাকে বলে Monomorphic (বিদ্যুৎ গতি)। যদি ৫টির বেশি ভিন্ন টাইপ পাস করা হয়, তা Megamorphic হয়ে যায় এবং V8 অপ্টিমাইজেশন বন্ধ করে সাধারণ স্লো প্রোপার্টি সার্চ করে।

Event Loop: প্রতি ফ্রেম রেন্ডার হওয়ার আগে ব্রাউজার সমস্ত Microtasks (Promise.then, queueMicrotask) খালি না হওয়া পর্যন্ত এক্সিকিউট করে। এরপরেই কেবল ম্যাক্রোটাস্ক (setTimeout, DOM events) প্রসেস হয়।

Modern @ngrx/signals (SignalStore): অ্যাঙ্গুলার কমিউনিটির আধুনিক প্রিয় পছন্দ। সিগন্যাল-ফার্স্ট, ডিপ ফাংশনাল এবং কম্পোজেবল। কোনো বিরক্তিকর অ্যাকশন-রিডিউসার ড্রাফট ছাড়াই signalStore(withState(...), withMethods(...), withComputed(...)) দিয়ে মাত্র ১০ লাইনে সম্পূর্ণ টাইপ-সেফ এন্টারপ্রাইজ স্টেট ম্যানেজমেন্ট করা যায়। মেমোরি ফুটপ্রিন্ট অনেক কম এবং দ্রুততর।

Architecture Paradigm 🟡 Mid-Level (2-5 Yrs)
৯৬. Monolithic বনাম Microservices Architecture: কখন মাইক্রোসার্ভিসে যাবেন এবং কখন যাবেন না?

Monolith: সমস্ত বিজনেস মডিউল একটি একক কোডবেস এবং একক ডেপ্লয়েবল ইউনিট হিসেবে রান করে। সুবিধা: দ্রুত ডেভেলপমেন্ট, সহজ ডিবাগিং, কোনো নেটওয়ার্ক ল্যাটেন্সি নেই, সিঙ্গেল ডাটাবেজ ট্রানজ্যাকশন (ACID)। অসুবিধা: টিম বড় হলে কোড কনফ্লিক্ট বাড়ে, যেকোনো ছোট পরিবর্তনের জন্য পুরো সিস্টেম রি-ডেপ্লয় করতে হয়।

Microservices: ব্যবসায়িক ডোমেইন অনুযায়ী স্বাধীন ছোট ছোট সার্ভিস (User, Order, Payment) যা নিজস্ব ডাটাবেজ মেইনটেইন করে এবং নেটওয়ার্কে (REST/gRPC/Kafka) যোগাযোগ করে।

কখন যাবেন না: স্টার্টআপ বা প্রজেক্টের প্রাথমিক পর্যায়ে কখনই মাইক্রোসার্ভিস শুরু করবেন না (Martin Fowler's Monolith First)। ডিস্ট্রিবিউটেড সিস্টেমের ওভারহেড (নেটওয়ার্ক ফেইলিওর, ডেটা ইনকনসিস্টেন্সি, সিআই/সিডি জটিলতা) ছোট টিমের সক্ষমতা নষ্ট করে দেয়। যখন কোনো নির্দিষ্ট মডিউলে অস্বাভাবিক ট্রাফিক আসে বা ১০০+ ইঞ্জিনিয়ারের দল স্বাধীনভাবে কাজ করতে চায়, কেবল তখনই মাইক্রোসার্ভিসে ভাগ করুন।

Scalability & Balancing 🟡 Mid-Level (2-5 Yrs)
৯৭. Horizontal vs Vertical Scaling কী? Load Balancing এর প্রধান অ্যালগরিদমগুলো কী কী?

Vertical Scaling (Scale Up): বিদ্যমান সিঙ্গেল সার্ভারে আরও বেশি CPU, RAM যুক্ত করা। একটি নির্দিষ্ট সীমার পর এটি অত্যন্ত ব্যয়বহুল এবং Single Point of Failure (SPOF)।

Horizontal Scaling (Scale Out): লোড ব্যালেন্সারের পেছনে একের অধিক সাধারণ সার্ভার ইনস্ট্যান্স যুক্ত করা। আধুনিক ক্লাউড সিস্টেমে এটিই মূল আর্কিটেকচার।

প্রধান অ্যালগরিদম: Round Robin (ক্রমানুসারে পাঠায়), Least Connections (যে সার্ভারে সবচেয়ে কম অ্যাক্টিভ ক্লায়েন্ট আছে), IP Hash (আইপি হ্যাশ করে সর্বদা একই সার্ভারে পাঠায় - Sticky Session)।

API Protocols 🟡 Mid-Level (2-5 Yrs)
৯৮. REST বনাম gRPC বনাম GraphQL এর আর্কিটেকচারাল ট্রেড-অফ ব্যাখ্যা করুন।

REST (HTTP/1.1 + JSON): সার্বজনীন ও সহজ ডিবাগিংযোগ্য। ব্রাউজার টু ব্যাকএন্ড পাবলিক এপিআই-র জন্য ডি-ফ্যাক্টো স্ট্যান্ডার্ড। কিন্তু টেক্সট-বেসড হওয়ায় পেলোড বড় হয়।

gRPC (HTTP/2 + Protocol Buffers): বাইনারি সিরিয়ালাইজেশন ফরম্যাট। অত্যন্ত দ্রুত এবং ব্যান্ডউইথ খরচ JSON-এর তুলনায় ৭০% কম। একই TCP কানেকশনে মাল্টিপ্লেক্সিং ও স্ট্রিমিং সমর্থন করে। ব্যবহার: ইন্টারনাল মাইক্রোসার্ভিস টু মাইক্রোসার্ভিস হাই-পারফরম্যান্স যোগাযোগ।

GraphQL: ক্লায়েন্ট একটি একক এন্ডপয়েন্টে কোয়েরি পাঠিয়ে ঠিক যে ফিল্ড দরকার শুধুমাত্র সেগুলোই চায়। মোবাইল অ্যাপ্লিকেশনে Over-fetching এবং Under-fetching সম্পূর্ণ দূর করে।

Distributed Systems 🟡 Mid-Level (2-5 Yrs)
৯৯. Idempotency Key কী এবং পেমেন্ট সিস্টেমে কেন এটি অত্যন্ত গুরুত্বপূর্ণ?

ডিস্ট্রিবিউটেড সিস্টেমে নেটওয়ার্ক ফেইলিওরের কারণে ক্লায়েন্ট একই রিকোয়েস্ট একাধিকবার পাঠাতে পারে। যদি ইউজার পেমেন্ট করার পর টাইমআউট পেয়ে পুনরায় সাবমিট করে, তার কার্ড থেকে দুবার টাকা কাটা একটি মারাত্মক ত্রুটি।

Idempotency Key: ক্লায়েন্ট প্রতি ট্রানজ্যাকশনে একটি ইউনিক Idempotency-Key: UUID হেডারে পাঠায়। সার্ভার ডাটাবেজ বা Redis এ চেক করে কি-টি ইতোমধ্যে প্রসেস হয়েছে কি না। প্রসেস হয়ে থাকলে সে পুনরায় চার্জ না করে পূর্বের সেভ করা রেজাল্ট রিটার্ন করে।

Microservices Data 🔴 Senior / Lead (5-7+ Yrs)
১০০. Dual-Write Problem কী এবং Transactional Outbox Pattern কীভাবে ডেটা কনসিস্টেন্সি রক্ষা করে?

যখন একটি সার্ভিস একই সাথে ডাটাবেজে অর্ডার সেভ করে এবং কাফকাতে ইভেন্ট পাবলিশ করতে চায়: ডাটাবেজ সেভ সফল হলেও যদি কাফকা ডাউন থাকার কারণে মেসেজ ড্রপ হয়, তবে সিস্টেম স্থায়ীভাবে ইনকনসিস্টেন্ট হয়ে যায়।

Transactional Outbox: কাফকাতে সরাসরি না পাঠিয়ে, একই লোকাল ডাটাবেজ ট্রানজ্যাকশনে Orders এবং OutboxMessages টেবিলে ইভেন্ট সেভ করা হয় (Atomic Commit)। এরপর একটি ব্যাকগ্রাউন্ড মেসেজ রিলে (যেমন Debezium CDC) ডাটাবেজের ট্রানজ্যাকশন লগ পড়ে কাফকাতে পুশ করে। এটি নেটওয়ার্ক ক্র্যাশেও মেসেজ হারানোর ঝুঁকি সম্পূর্ণ দূর করে (At-least-once delivery)।

Fault Tolerance 🔴 Senior / Lead (5-7+ Yrs)
১০১. Circuit Breaker (Polly) এর ৩টি স্টেট কীভাবে ক্যাসকেডিং ফেইলিওর ঠেকায়?

যখন কোনো ডাউনস্ট্রিম থার্ড-পার্টি সার্ভিস ডাউন থাকে, ইনকামিং হাজার হাজার রিকোয়েস্ট থ্রেড ব্লক করে বসে থাকে এবং এক সার্ভিসের কারণে পুরো ক্লাস্টার ভেঙে পড়ে (Cascading Failure)।

Circuit Breaker ৩টি স্টেটে পরিচালিত হয়:

  • Closed (স্বাভাবিক): রিকোয়েস্ট স্বাভাবিকভাবে পাস হয় এবং ফেইলিওর রেট পর্যবেক্ষণ করা হয়।
  • Open (সার্কিট ব্রেক): ফেইলিওর রেট ৫০% অতিক্রম করলে সার্কিট ওপেন হয়ে যায়। ডাউনস্ট্রিমে কোনো নেটওয়ার্ক কল না পাঠিয়ে তাৎক্ষণিকভাবে ফলব্যাক রেসপন্স ফেরত দেয়।
  • Half-Open (টেস্টিং): নির্দিষ্ট বিরতির পর ১-২টি ট্রায়াল রিকোয়েস্ট পাঠায়। সফল হলে স্বাভাবিক স্টেটে ফেরে, ফেইল হলে আবার ওপেন স্টেটে লক থাকে।
Distributed Transactions 🔴 Senior / Lead (5-7+ Yrs)
১০২. Distributed Transactions: Two-Phase Commit (2PC) বনাম Saga Pattern (Choreography vs Orchestration)?

Two-Phase Commit (2PC): সেন্ট্রাল কোঅর্ডিনেটর সমস্ত পার্টিসিপ্যান্ট নোডকে লক করে। ক্লাউডে এটি অ্যান্টি-প্যাটার্ন কারণ নেটওয়ার্ক ড্রপে পুরো সিস্টেম লক হয়ে থমকে যায়।

Saga Pattern: লোকাল ট্রানজ্যাকশনের একটি ধারাবাহিক সিকোয়েন্স। কোনো ধাপ ব্যর্থ হলে আগের সমস্ত সফল ধাপকে রিভার্স করার জন্য Compensating Transaction চালানো হয়।

  • Choreography: প্রতিটি সার্ভিস ইভেন্ট শুনে নিজের কাজ করে পরবর্তী ইভেন্ট ছাড়ে। সেন্ট্রাল কন্ট্রোলার থাকে না (ছোট প্রজেক্টের জন্য)।
  • Orchestration: একটি সেন্ট্রাল অর্কেস্ট্রেটর (MassTransit State Machine) ধাপে ধাপে নির্দেশ পাঠায় এবং ফেইল করলে সুনির্দিষ্ট ক্ষতিপূরণমূলক রোলব্যাক চালায় (জটিল ফাইন্যান্সিয়াল সিস্টেমের জন্য সেরা)।
Event Streaming 🔴 Senior / Lead (5-7+ Yrs)
১০৩. Apache Kafka Internals: Partition, Consumer Group, Rebalancing এবং Exactly-Once Semantics (EOS)?

Topic & Partition: কাফকা টপিক এক বা একাধিক পার্টিশনে বিভক্ত থাকে যা ডিস্কে অ্যাপেন্ড-অনলি কমিট লগ হিসেবে থাকে। পার্টিশনই হলো কাফকার সমান্তরাল স্কেলিংয়ের একক।

Consumer Group & Rebalancing: একটি গ্রুপের কনজিউমারদের মাঝে পার্টিশনগুলো বণ্টিত হয়। কনজিউমার ক্র্যাশ করলে গ্রুপ কোঅর্ডিনেটর পার্টিশনগুলোকে সুস্থ মেম্বারদের মাঝে পুনর্বণ্টন (Rebalance) করে দেয়।

Exactly-Once Semantics (EOS): আইডেম্পোটেন্ট প্রডিউসার (enable.idempotence=true) এবং ট্রানজ্যাকশনাল প্রডিউসার দিয়ে নিশ্চিত করা হয় যে নেটওয়ার্ক ড্রপ হলেও ডুপ্লিকেট মেসেজ তৈরি হবে না এবং এন্ড-টু-এন্ড ডাটা একবারই প্রসেস হবে।

High Scale Case Study 🔴 Senior / Lead (5-7+ Yrs)
১০৪. ফ্ল্যাশ সেল বা টিকিট বুকিং সিস্টেমে লাখ লাখ কনকারেন্ট ট্রাফিকে ডাটাবেজ ক্র্যাশ না করিয়ে কীভাবে হ্যান্ডেল করবেন?

ফ্ল্যাশ সেলে ডাটাবেজে সরাসরি কল করা নিষিদ্ধ:

  1. ইন-মেমোরি স্টক ম্যানেজমেন্ট (Redis Lua Script): স্টকের সংখ্যা Redis-এ ক্যাশ থাকে। DECRBY লজিকটি একটি সিঙ্গেল অ্যাটমিক Redis Lua স্ক্রিপ্টে চালানো হয়। স্টক ০ হলে ইনস্ট্যান্ট "Sold Out" বলে ফেরত পাঠানো হয়।
  2. অ্যাসিঙ্ক অর্ডার প্লেসমেন্ট (Kafka Queue): যারা স্টক সফলভাবে ডিক্রিমেন্ট করতে পেরেছে তাদের অর্ডার ইভেন্ট কাফকা কিউতে পাঠিয়ে দেওয়া হয়।
  3. ডাটাবেজ ব্যাচ রাইটার: ব্যাকগ্রাউন্ড ওয়ার্কার সার্ভিস কাফকা থেকে প্রতি সেকেন্ডে ১০০-২০০টি করে অর্ডার ব্যাচ আকারে ডাটাবেজে পারসিস্ট করে।
API Rate Limiting 🔴 Senior / Lead (5-7+ Yrs)
১০৫. API Rate Limiting: Token Bucket, Leaky Bucket এবং Sliding Window Counter এর মেকানিক্স ব্যাখ্যা করুন।

Token Bucket: বালতিতে প্রতি সেকেন্ডে নির্দিষ্ট হারে টোকেন জমা হয়। রিকোয়েস্ট এলে ১টি টোকেন নিয়ে পাস হয়। ফাঁকা থাকলে রিকোয়েস্ট বাতিল (HTTP 429)। সাময়িক বাস্ট ট্রাফিক অনুমোদন করে।

Leaky Bucket: রিকোয়েস্টগুলো কিউতে জমা হয় এবং নিচের ছিদ্র দিয়ে স্থির গতিতে প্রসেস হয়। কোনো বাস্ট অ্যালাউ করে না।

Sliding Window Counter (Redis): বর্তমান সময় এবং বিগত ৬০ সেকেন্ডের বাউন্ডারিকে স্লাইডিং উইন্ডো আকারে পর্যবেক্ষণ করে রিয়েল-টাইমে নিখুঁত রেট লিমিট নিশ্চিত করে।

Distributed Partitioning 🔴 Senior / Lead (5-7+ Yrs)
১০৬. Consistent Hashing with Virtual Nodes: ক্যাশিং নোড যোগ/বিয়োগের সময় রিব্যালেন্সিং কীভাবে সমাধান করে?

সাধারণ হ্যাশিংয়ে hash(key) % N ব্যবহার করা হয়। কিন্তু একটি নোড মারা গেলে বা যোগ হলে (N পরিবর্তিত হলে) ৯৯% ক্যাশ মিস হয়ে সম্পূর্ণ ক্যাশ ক্লাস্টার ধ্বংস হয়ে যায়।

Consistent Hashing: একটি কাল্পনিক বৃত্তাকার Hash Ring (0 থেকে 2^32-1) তৈরি করে। সার্ভার এবং ডেটা কি উভয়কেই এই রিংয়ে হ্যাশ করে ম্যাপ করা হয়। প্রতিটি ডেটা কি ঘড়ির কাঁটার দিকে প্রথম সার্ভারে স্থান পায়। কোনো সার্ভার বাদ পড়লে শুধুমাত্র তার পার্শ্ববর্তী নোডের ক্যাশ রি-হ্যাশ হয়, বাকি ৯৫% ক্যাশ অক্ষত থাকে।

Virtual Nodes (ভার্চুয়াল নোড): ডেটার অসম বণ্টন (Hotspots) রোধ করতে প্রতিটি ফিজিক্যাল সার্ভারকে রিংয়ের বিভিন্ন বিন্দুতে ১০০-২০০টি ভার্চুয়াল নোড হিসেবে ছড়িয়ে দেওয়া হয়, যা নিখুঁত সুষম ভারসাম্য (Uniform Distribution) নিশ্চিত করে।

Database Sharding 🔴 Senior / Lead (5-7+ Yrs)
১০৭. Database Sharding: Range-based বনাম Hash-based Sharding এবং Cross-shard Query কীভাবে হ্যান্ডেল করবেন?

যখন ডাটাবেজ টেবিল এত বড় হয়ে যায় যে সিঙ্গেল মেশিনের ডিস্ক বা মেমোরিতে ধরে না, তখন অনুভূমিকভাবে ডেটাকে একাধিক স্বাধীন ডাটাবেজ নোডে ভাগ করাকে Sharding বলে।

  • Range-based Sharding: নির্দিষ্ট সীমার ভিত্তিতে ভাগ করা (যেমন: ইউজার আইডি ১-১ মিলিয়ন Shard 1 এ, ১-২ মিলিয়ন Shard 2 এ)। রেঞ্জ কুয়েরি সহজ কিন্তু নতুন ব্যবহারকারীদের কারণে শেষ শার্ডে হটস্পট হয়।
  • Hash-based Sharding: hash(UserId) % TotalShards। ডেটা সুষমভাবে ছড়ায় কিন্তু রেঞ্জ কোয়েরি অত্যন্ত কঠিন।
  • Cross-shard Queries & Joins: দুটি ভিন্ন শার্ডের টেবিল সরাসরি SQL JOIN করা যায় না। সমাধান: অ্যাপ্লিকেশন লেভেলে প্যারালাল কুয়েরি চালিয়ে মেমোরিতে মার্চ করা (Scatter-Gather Pattern), অথবা গ্লোবাল লুকআপ টেবিল আলাদা ক্যাশে রাখা।
Event-Driven Architecture 🔴 Senior / Lead (5-7+ Yrs)
১০৮. Event Sourcing এবং CQRS: Aggregate Snapshots এবং Read Model Projections কীভাবে তৈরি হয়?

Event Sourcing: বর্তমান স্টেট সরাসরি ডাটাবেজে ওভাররাইট না করে, সিস্টেমে যা যা ঘটেছে তার সমস্ত অপরিবর্তনশীল ঘটনাকে (Events) একটি Append-Only Event Store-এ ক্রমানুসারে সংরক্ষণ করা হয় (যেমন: AccountCreated, MoneyDeposited, MoneyWithdrawn)।

  • Aggregate Reconstitution: অবজেক্টের বর্তমান ব্যালেন্স জানতে সমস্ত পুরানো ইভেন্ট প্রথম থেকে রি-প্লে (Replay) করা হয়।
  • Snapshots: ১ লাখ ইভেন্ট রি-প্লে করা ধীরগতির হওয়ায় প্রতি ১,০০০ ইভেন্ট পর পর একটি স্টেট স্ন্যাপশট নিয়ে রাখা হয়।
  • Projections (Read Models): ব্যাকগ্রাউন্ড প্রজেকশন সার্ভিস ইভেন্টগুলো শুনে রিলেশনাল DB বা Elasticsearch এ ডিনরমালাইজড রিড মডেল তৈরি করে রাখে, যাতে ইউজাররা মিলি-সেকেন্ডে কুয়েরি করতে পারে।
Distributed Consensus 🔴 Senior / Lead (5-7+ Yrs)
১০৯. Distributed Consensus: Raft অ্যালগরিদম কীভাবে Leader Election, Log Replication এবং Split-Brain রোধ করে?

ডিস্ট্রিবিউটেড ক্লাস্টারে (যেমন Kafka, Etcd, Consul) সমস্ত নোড যেন একই স্টেট মেনে চলে তার জন্য Raft Consensus ব্যবহৃত হয়:

  1. Leader Election: ক্লাস্টারের নোড ৩টি স্টেটে থাকে (Follower, Candidate, Leader)। প্রতিটি নোডের একটি র‍্যান্ডম হার্টবিট টাইমার থাকে। লিডারের হার্টবিট মিস হলে নোড Candidate হয়ে ভোট চায়। সংখ্যাগরিষ্ঠ ভোট (Quorum: (N/2) + 1) পেলে সে নতুন Leader হয়।
  2. Log Replication: ক্লায়েন্ট লিডারকে রাইট পাঠায়। লিডার সমস্ত ফলোয়ার নোডে লগ রেপ্লিকেট করে এবং সংখ্যাগরিষ্ঠ নোড লগ রাইট কনফার্ম করলে লিডার ট্রানজ্যাকশন কমিট করে।
  3. Split-Brain প্রতিরোধ: ৫টি নোডের ক্লাস্টার ভেঙে ২ এবং ৩ নোডে ভাগ হলে, ৩ নোডের পক্ষই কেবল সংখ্যাগরিষ্ঠ কোরাম গঠন করতে পারে। ২ নোডের পক্ষ কোনো সিদ্ধান্ত কমিট করতে পারে না, ফলে ডেটা করাপশন রোধ হয়।
Distributed Locking Fencing 🔴 Senior / Lead (5-7+ Yrs)
১১০. Martin Kleppmann এর RedLock সমালোচনা কী এবং Fencing Tokens কীভাবে রেস কন্ডিশন সমাধান করে?

মার্টিন ক্লেপম্যান প্রমাণ করেন যে বিশুদ্ধ টাইম-বেসড রেডিস ডিস্ট্রিবিউটেড লক (RedLock) শতভাগ নিরাপদ নয়।

ভুল সিনারিও: Client 1 লক নিল। হঠাৎ Client 1-এ একটি দীর্ঘ GC Pause বা নেটওয়ার্ক স্টল হলো। এর মাঝে লকের TTL এক্সপায়ার হয়ে গেল এবং Client 2 নতুন লক পেয়ে কাজ শুরু করল। Client 1 যখন আনফ্রিজ হলো, সে মনে করল লক এখনও তার কাছেই আছে এবং সে ফাইল রাইট করে Client 2 এর ডেটা ওভাররাইট করে ফেলল!

Fencing Token এর সমাধান: লক নেওয়ার সময় সার্ভার একটি ক্রমবর্ধমান টোকেন (Monotonically Increasing Number, যেমন: টোকেন ৩৪, ৩৫) প্রদান করে। স্টোরেজ বা ডাটাবেজ যেকোনো রাইট গ্রহণের আগে চেক করে: যদি আগত রিকোয়েস্টের টোকেন পূর্বের প্রসেস করা সর্বোচ্চ টোকেনের চেয়ে কম হয়, তবে সে রাইট তাৎক্ষণিকভাবে রিজেক্ট করে দেয়।

Real-time at Scale C1000K 🔴 Senior / Lead (5-7+ Yrs)
১১১. ১ মিলিয়ন কনকারেন্ট WebSocket কানেকশন (C1000K Problem) হ্যান্ডেল করার আর্কিটেকচার কীভাবে সাজাবেন?

১০ লাখ লাইভ ওয়েবসকেট ক্লায়েন্ট ধরে রাখতে অপারেটিং সিস্টেম ও আর্কিটেকচারাল সমন্বয় প্রয়োজন:

  2. Epoll I/O Multiplexing: প্রতি কানেকশনে ১টি করে থ্রেড রাখা অসম্ভব। লিনাক্সের Epoll মেকানিজমে একটি সিঙ্গেল ইভেন্ট-লুপ থ্রেড লক্ষ লক্ষ নিষ্ক্রিয় সকেট কানেকশন হ্যান্ডেল করে (Kestrel Transport Sockets)।
  3. Redis Pub/Sub Backplane: ইউজাররা বিভিন্ন ক্লাস্টার সার্ভারে যুক্ত থাকে। Server A-তে থাকা ব্যবহারকারী Server B-এর কোনো ফ্রেন্ডকে মেসেজ পাঠালে মাঝখানে Redis Pub/Sub বা RabbitMQ ব্যাকপ্লেন মেসেজ রাউটিং পরিচালনা করে।

একটি ইউজার রিকোয়েস্ট যদি ৭টি মাইক্রোসার্ভিস পার করে আসে, একটি সেন্ট্রাল ট্রেস আইডি ছাড়া এরর ডিবাগ করা অসম্ভব।

  • 00f067... হলো SpanId (প্রতিটি নির্দিষ্ট সার্ভিসের কাজের একক)।

Distributed Transactions TCC 🔴 Senior / Lead (5-7+ Yrs)
১১৩. TCC (Try-Confirm-Cancel) প্যাটার্ন কী এবং পেমেন্ট গেটওয়েতে Saga এর চেয়ে এটি কখন বেশি উপযোগী?

Saga এর সীমাবদ্ধতা: সাগাতে প্রতিটি ধাপ সরাসরি আসল টাকা কেটে ফেলে। শেষের ধাপে ফেইল করলে ক্ষতিপূরণমূলক ট্রানজ্যাকশনে টাকা রিফান্ড করা হয়—যা গ্রাহকের ব্যাংক স্টেটমেন্টে বিভ্রান্তি তৈরি করে।

TCC ৩ ধাপে কাজ করে:

  1. Try: টাকা না কেটে শুধুমাত্র নির্দিষ্ট ব্যালেন্স রিজার্ভ বা ফ্রিজ (Hold) করে রাখে।
  2. Confirm: সমস্ত ডিপেনডেন্ট সার্ভিস সফল হলে রিজার্ভ করা টাকা একবারে Deduct করে ট্রানজ্যাকশন সম্পন্ন করে।
  3. Cancel: কোনো একটি সার্ভিস ফেইল করলে রিজার্ভ করা হোল্ডটি রিলিজ করে দেয় (গ্রাহকের একাউন্টে কোনো কাটাছেঁড়া ছাড়াই)।
Disaster Recovery RTO RPO 🔴 Senior / Lead (5-7+ Yrs)
১১৪. Disaster Recovery: RTO বনাম RPO কী? Multi-Region Active-Active আর্কিটেকচার কীভাবে ডিজাইন করবেন?

RTO (Recovery Time Objective): একটি ডাটা সেন্টার পুড়ে বা ডাউন হয়ে যাওয়ার পর কত সময়ের ভেতর সিস্টেম রিস্টোর করতে হবে (যেমন: সর্বোচ্চ ১৫ মিনিট)।

RPO (Recovery Point Objective): দুর্যোগের সময় সর্বোচ্চ কতটুকু সাম্প্রতিক ডেটা হারানোর ঝুঁকি ব্যবসা মেনে নেবে (যেমন: ০ সেকেন্ড বা সর্বোচ্চ ২ মিনিট)।

Multi-Region Active-Active আর্কিটেকচার: দুটি ভিন্ন ভৌগোলিক ক্লাউড রিজিয়নে (যেমন: AWS ফ্রাঙ্কফুর্ট ও সিঙ্গাপুর) সম্পূর্ণ অ্যাপ ও ডাটাবেজ সমান্তরালে লাইভ থাকে। ক্লায়েন্ট ট্রাফিক Route 53 Geolocation / Latency Routing দিয়ে নিকটবর্তী রিজিয়নে পাঠানো হয়। ডাটাবেজে মাল্টি-মাস্টার বাই-ডিরেকশনাল রেপ্লিকেশন (Conflict-Free Replicated Data Types - CRDTs) নিশ্চিত করা হয়।

Caching Topologies 🔴 Senior / Lead (5-7+ Yrs)
১১৫. Caching Topologies: Write-Through বনাম Write-Behind (Write-Back) এবং Cache Invalidation স্ট্রেটেজি?

Write-Through: অ্যাপ ক্যাশে ডাটা লেখে এবং ক্যাশ প্রোভাইডার সিনক্রোনাসলি ডাটাবেজে ডাটা সেভ করে। উভয়ই সফল হলে কনফার্মেশন ফেরত আসে। ক্যাশ এবং ডাটাবেজ সর্বদা ১০০% কনসিস্টেন্ট থাকে কিন্তু রাইট ল্যাটেন্সি বেশি।

Write-Behind (Write-Back): অ্যাপ দ্রুত মেমোরি ক্যাশে ডাটা লিখে ইউজারকে ওকে বলে দেয়। ক্যাশ ইঞ্জিন ব্যাকগ্রাউন্ডে ব্যাচ আকারে ডাটাবেজে ডেটা পারসিস্ট করে। রাইট বিদ্যুৎগতি সম্পন্ন হলেও সার্ভার হঠাৎ ক্র্যাশ করলে মেমোরির ডাটা হারানোর ঝুঁকি থাকে।

Cache Invalidation: সবচেয়ে জনপ্রিয় হলো Cache-Aside (Lazy Loading)। আপডেটের সময় ক্যাশ আপডেট না করে সরাসরি Delete (Evict) করে দেওয়া হয়। পরবর্তী রিড রিকোয়েস্ট ক্যাশ মিস করে নতুন ডাটাবেজ ভ্যালু এনে ক্যাশ পপুলেট করে নেয়।

Edge Computing & CDN 🔴 Senior / Lead (5-7+ Yrs)
১১৬. CDN Edge Caching: stale-while-revalidate এবং Cloudflare Workers কীভাবে অরিজিন সার্ভারের ৯০% লোড কমায়?

stale-while-revalidate হেডার:

ক্যাশ এক্সপায়ার হওয়ার পরও এজ ক্যাশ ক্লায়েন্টকে দ্রুত পুরানো ক্যাশ রেসপন্স ফেরত দেয় (জিরো ল্যাটেন্সি) এবং পেছনের ব্যাকগ্রাউন্ডে সম্পূর্ণ স্বাধীনভাবে অরিজিন সার্ভার থেকে নতুন ডাটা এনে ক্যাশ রিফ্রেশ করে নেয়।

Edge Workers: ব্যবহারকারীর নিকটবর্তী ক্লাউডফ্লেয়ার বা ক্লাউডফ্রন্ট এজ পপ (PoP) এ লাইটওয়েট V8 আইসোলেটে কোড এক্সিকিউট করে। জিও-রিডাইরেকশন, অথেনটিকেশন JWT ভ্যালিডেশন এবং এ/বি টেস্টিং অরিজিন সার্ভারে পৌঁছানোর আগেই এজ থেকেই নিষ্পন্ন হয়ে যায়।

Async Request-Reply 🔴 Senior / Lead (5-7+ Yrs)
১১৭. Asynchronous Request-Reply Pattern: দীর্ঘায়িত ভারী ব্যাকগ্রাউন্ড প্রসেসিংয়ে HTTP 202 Accepted কীভাবে কাজ করে?

যদি কোনো রিকোয়েস্ট সম্পন্ন হতে ৩০ সেকেন্ড বা তার বেশি সময় লাগে (যেমন: ১ লাখ রো-র এক্সেল রিপোর্ট তৈরি বা ভিডিও ট্রান্সকোডিং), সরাসরি HTTP কানেকশন ধরে রাখলে গেটওয়ে ৫০৪ টাইমআউট দেয়।

সমাধান:

  1. ক্লায়েন্ট রিকোয়েস্ট পাঠালে সার্ভার জবটি কিউতে পুশ করে তাৎক্ষণিকভাবে ফেরত দেয়: HTTP 202 Accepted সাথে হেডারে Location: /api/jobs/123/status এবং Retry-After: 10।
  2. ক্লায়েন্ট প্রতি ১০ সেকেন্ড পর পর স্ট্যাটাস ইউআরএলে পোলিং করে প্রগ্রেস চেক করে।
  3. কাজ শেষ হলে স্ট্যাটাস এন্ডপয়েন্ট HTTP 303 See Other দিয়ে প্রস্তুত ফাইলের ডাউনলোড লিঙ্ক ফেরত দেয়।
Resilience Patterns 🔴 Senior / Lead (5-7+ Yrs)
১১৮. Bulkhead Pattern: কীভাবে থ্রেডপুল ও মেমোরি আইসোলেশন দিয়ে একটি স্লো সার্ভিস থেকে সম্পূর্ণ সিস্টেমকে রক্ষা করবেন?

জাহাজের খোলে বিভিন্ন চেম্বারের মাঝে যেমন জলরোধী দেওয়াল (Bulkhead) থাকে যাতে একটি চেম্বার ফুটো হলেও পুরো জাহাজ না ডোবে—ঠিক তেমনি সফটওয়্যারেও রিসোর্স আইসোলেশন করা হয়।

বাস্তবায়ন: পেমেন্ট গেটওয়ে, ইনভেন্টরি সার্ভিস এবং সাধারণ ক্যাটালগ সার্ভিসের জন্য পৃথক ডেডিকেটেড থ্রেডপুল বা SemaphoreSlim বরাদ্দ করা হয়। যদি পেমেন্ট গেটওয়ে হঠাৎ স্লো হয়ে পড়ে, তবে শুধুমাত্র তার জন্য নির্ধারিত ২০টি থ্রেডই ব্লক হবে। ক্যাটালগ বা সার্চ সার্ভিসের বরাদ্দকৃত বাকি ৮০টি থ্রেড সম্পূর্ণ মুক্ত থাকবে এবং ইউজাররা স্বাভাবিকভাবে সাইট ব্রাউজ করতে পারবে।

Reactive Backpressure 🔴 Senior / Lead (5-7+ Yrs)
১১৯. Reactive Backpressure: প্রোডিউসারের গতি কনজিউমারের চেয়ে ১০ গুণ বেশি হলে কীভাবে বাফার ব্লো-আপ ঠেকাবেন?

যদি একটি সেন্সর বা মেসেজ স্ট্রিম প্রতি সেকেন্ডে ১০,০০০ মেসেজ পাঠায় অথচ ডাটাবেজ সেভার মাত্র ১,০০০ মেসেজ প্রসেস করতে পারে, রিসিভারের মেমোরি ফুল হয়ে অ্যাপ ক্র্যাশ করবে।

Backpressure Strategies:

  • Request-driven (Pull-based): কনজিউমার প্রোডিউসারকে বলে: "আমি এখন প্রস্তুত, আমাকে পরবর্তী ১০০টি আইটেম দাও।"
  • Drop Strategy: বাফার পূর্ণ হলে ইনকামিং অপ্রয়োজনীয় মেসেজ ড্রপ করা (যেমন ভিডিও স্ট্রিমিংয়ে ফ্রেম ড্রপ)।
  • Buffer with Sliding Window: নতুন মেসেজ অগ্রাধিকার দিয়ে পুরানো মেসেজ মুছে ফেলা (Latest Wins)।

১২০. API Gateway এবং BFF (Backend-for-Frontend) প্যাটার্ন: Microsoft YARP দিয়ে কীভাবে উচ্চগতির গেটওয়ে তৈরি করবেন?

BFF Pattern: মোবাইল অ্যাপ, ওয়েব ব্রাউজার এবং থার্ড-পার্টি পার্টনারদের রিকোয়ারমেন্ট ভিন্ন ভিন্ন হয়। একটি একক জেনেরিক এপিআই না বানিয়ে প্রতি ক্লায়েন্ট চ্যানেলের জন্য ডেডিকেটেড লাইটওয়েট ব্যাকএন্ড গেটওয়ে (BFF) তৈরি করা হয়।

Microsoft YARP (Yet Another Reverse Proxy): সম্পূর্ণ .NET 8/9 এ তৈরি অত্যন্ত দ্রুতগতির রিভার্স প্রক্সি টুলকিট। কন্ট্রোলারের বয়লারপ্লেট ছাড়াই কনফিগারেশনে সরাসরি রাউটিং, রাউন্ড-রবিন ক্লাস্টারিং, পাথ ট্রান্সফর্ম, এবং রেট-লিমিটিং পরিচালনা করে। এটি মাইক্রোসফটের অভ্যন্তরীণ বিং ও অ্যাজুরের কোটি কোটি রিকোয়েস্ট সফলভাবে সার্ভ করে।

১৩১. Linux Kernel Networking Tuning: sysctl.conf টিউন করে TIME_WAIT Socket Exhaustion কীভাবে দূর করবেন?

উচ্চ ট্রাফিকের মাইক্রোসার্ভিসে দ্রুত আউটগোয়িং HTTP কল করলে হাজার হাজার সকেট TIME_WAIT স্টেটে আটকে থাকে এবং নতুন সকেটের জন্য পোর্ট খালি না পেয়ে SocketException: Address already in use এরর দেয়।

/etc/sysctl.conf প্রোডাকশন কার্নেল টিউনিং:

# ইনকামিং TCP কানেকশন ব্যাকলগ বাড়ানো (ডিফল্ট ১২৮ থেকে ৬৫৫৩৫)
net.core.somaxconn = 65535

# TIME_WAIT সকেট দ্রুত রি-ইউজ করার অনুমোদন
net.ipv4.tcp_tw_reuse = 1

# লোকাল পোর্ট রেঞ্জ সর্বোচ্চ বৃদ্ধি করা (১০২৪ থেকে ৬৫৫৩৫)
net.ipv4.ip_local_port_range = 1024 65535

# SYN Flood অ্যাটাক প্রটেকশন
net.ipv4.tcp_max_syn_backlog = 16384

sysctl -p চালালে কার্নেল সেকেন্ডে লক্ষ লক্ষ হাই-স্পিড সকেট কানেকশন হ্যান্ডেল করতে সক্ষম হয়।

Windows Kernel HTTP.sys 🔴 Senior / Lead (5-7+ Yrs)
১৩২. Windows Kernel HTTP.sys Internals: কার্নেল ক্যাশিং এবং Kerberos Double-Hop সমস্যা ও SPN রেজিস্ট্রেশন?

HTTP.sys: উইন্ডোজ কার্নেল স্পেসে (Ring 0) চলে। এটি সরাসরি নেটওয়ার্ক ড্রাইভ থেকে HTTP প্যাকেট গ্রহণ করে। যদি কোনো স্ট্যাটিক ফাইল বা রেসপন্স কার্নেল ক্যাশে থাকে, ইউজার মোডের w3wp.exe প্রসেসে কোনো কনটেক্সট সুইচ ছাড়াই কার্নেল থেকেই রেসপন্স ফেরত পাঠিয়ে দেয়।

Kerberos Double-Hop Problem: যখন একজন ব্যবহারকারী ব্রাউজার থেকে IIS ওয়েবসাইটে উইন্ডোজ অথেনটিকেশন (NTLM/Kerberos) দিয়ে লগইন করে, IIS সার্ভিস অন্য কোনো ডাটাবেজ বা ব্যাকএন্ড সার্ভারে ব্যবহারকারীর আইডেন্টিটি পাস করতে পারে না (Double-Hop ড্রপ)।

সমাধান: ডোমেইন কন্ট্রোলারে সার্ভিসের জন্য Service Principal Name (SPN) রেজিস্টার করতে হয় (setspn -A HTTP/myportal domain\serviceaccount) এবং অ্যাক্টিভ ডিরেক্টরিতে Kerberos Constrained Delegation (KCD) কনফিগার করতে হয়।

১৩৩. Unmanaged / Native Memory Leaks: CLR ম্যানেজড হিপে কোনো লিক না থাকা সত্ত্বেও প্রোডাকশনে মেমোরি গ্রোথ কীভাবে ডিবাগ করবেন?

ডিবাগিং পদ্ধতি:

  1. উইন্ডোজে GFlags (Global Flags) দিয়ে ইউজার মোড স্ট্যাক ট্রেস অন করুন: gflags /i w3wp.exe +ust।

  3. তুলনামূলক বিশ্লেষণ চালান: umdh snap1.log snap2.log > diff.txt। ফাইলের শীর্ষে সরাসরি দেখা যাবে কোন আনম্যানেজড C++ মেথডের কারণে কোটি কোটি বাইট লিক হচ্ছে!

১৩৪. Kubernetes এ .NET পডের Graceful Termination এবং Cascading Restart Death Loop কীভাবে এড়াবেন?

Graceful Termination (.NET 8):

var app = builder.Build();
app.Lifetime.ApplicationStopping.Register(() => {
    // নতুন রিকোয়েস্ট গ্রহণ বন্ধ করো এবং রানিং ট্রানজ্যাকশন শেষ করার জন্য ১০ সেকেন্ড সময় দাও
});

Cascading Death Loop: যদি কোনো কারণে ডাটাবেজ স্লো হয়ে যায়, পডের Liveness Probe ফেইল করে। কুবারনেটিস তখন সমস্ত পড একসাথে কিল করে পুনরায় চালু করতে থাকে। নতুন শুরু হওয়া সমস্ত পড একসাথে আবার ডাটাবেজে কোল্ড স্টার্ট হিট করায় পুরো ক্লাস্টার চিরতরে ধসে পড়ে।

ফিক্স: Liveness Probes-এ কখনোই ডাটাবেজ রাখবেন না (শুধুমাত্র ইন্টারনাল প্রসেস পিং)। এবং PodDisruptionBudget (PDB) কনফিগার করুন যাতে একসাথে ক্লাস্টারের ২০% এর বেশি পড ডাউন না হতে পারে।

ফলাফল: বিগত দুই বছরে আমার টিমের ৩ জন ডেভেলপার সফলভাবে সিনিয়র রোলে পদোন্নতি লাভ করেছেন।

Incident Management 🔴 Senior / Lead (5-7+ Yrs)
১৪৪. প্রোডাকশনে বড় ধরণের বিভ্রাট (Major Outage) ঘটলে ইনসিডেন্ট ম্যানেজমেন্ট ও Blameless Post-Mortem কীভাবে পরিচালনা করেন?

লাইভ ইনসিডেন্টের সময়: টেক লিড হিসেবে শান্ত থেকে তাৎক্ষণিকভাবে Incident Commander এর ভূমিকা গ্রহণ করা। বিজনেস ও স্টেকহোল্ডারদের প্রতি ১৫ মিনিটে স্ট্যাটাস আপডেট দেওয়া যাতে ইঞ্জিনিয়াররা নিরবচ্ছিন্নভাবে ট্রাবলশুট করতে পারে। অগ্রাধিকার থাকে রুট কজ বের করার চেয়ে আগে সার্ভিস দ্রুত রিস্টোর (Mitigation) করা (যেমন ট্রাফিক ডাইভার্ট করা বা রোলব্যাক করা)।

ইনসিডেন্ট পরবর্তী (Blameless Post-Mortem): কোনো নির্দিষ্ট ব্যক্তিকে দোষারোপ না করে সিস্টেমের প্রসেসগত ফাঁকফোকর বের করা। আমরা 5 Whys Methodology প্রয়োগ করি: "কেন ডাটাবেজ ডাউন হলো? কারণ কানেকশন পুল ফুল ছিল। কেন পুল ফুল ছিল? কারণ একটি স্লো কুয়েরি লক ধরে রেখেছিল। কেন স্লো কুয়েরি প্রোডাকশনে গেল? কারণ স্ট্রেস টেস্টে এই সিনারিও কভার করা হয়নি।"

ফলাফল: অ্যাকশন আইটেম তৈরি করা যাতে একই ধরণের আউটেজ ভবিষ্যতে আর কখনো পুনরাবৃত্তি না ঘটে।

Architecture Governance 🔴 Senior / Lead (5-7+ Yrs)
১৪৫. Architecture Decision Records (ADR) কী? দল পরিবর্তন হলেও টেকনিক্যাল সিদ্ধান্তগুলো কীভাবে জীবন্ত রাখবেন?

সমস্যা: ২ বছর পর কোনো নতুন সিনিয়র ইঞ্জিনিয়ার এসে বলে: "এই সিস্টেমে কেন Kafka বাদ দিয়ে RabbitMQ নেওয়া হলো? এটা তো বাজে ডিজাইন!" কিন্তু সে জানে না ২ বছর আগের ক্লাউড বাজেট বা ট্রাফিক সীমাবদ্ধতা কেমন ছিল।

Architecture Decision Record (ADR): প্রতিটি গুরুত্বপূর্ণ টেকনিক্যাল সিদ্ধান্তের সময় রিপোজিটরির /docs/adr/ ফোল্ডারে একটি সংক্ষিপ্ত মার্কডাউন ফাইল লেখা হয়:

  1. Title: ADR-005: Use PostgreSQL instead of MongoDB.
  2. Status: Accepted / Deprecated / Superseded.
  3. Context: আমাদের ডেটা স্ট্রাকচার অত্যন্ত রিলেশনাল এবং কঠোর ACID ট্রানজ্যাকশন প্রয়োজন।
  4. Decision: আমরা PostgreSQL 16 বেছে নিয়েছি এবং JSONB ডেটার জন্য GIN ইনডেক্স ব্যবহার করব।
  5. Consequences: ইতিবাচক: স্ট্রং টাইপিং ও আর্থিক নির্ভরযোগ্যতা। নেতিবাচক: স্কিমা পরিবর্তনের সময় মাইগ্রেশন স্ক্রিপ্ট মেইনটেইন করতে হবে।

এটি প্রজেক্টে "Cargo Cult" বা অনুমান-নির্ভর পরিবর্তন চিরতরে বন্ধ করে দেয়।

Monolith Decomposition 🔴 Senior / Lead (5-7+ Yrs)
১৪৬. Monolith to Microservices Migration: ডোমেইন মডেল ভেঙে Bounded Context কীভাবে চিহ্নিত করবেন?

সরাসরি কোড ফাইল ভাগ না করে Domain-Driven Design (DDD) এর মাধ্যমে এগোতে হয়:

  1. Event Storming Workshop: বিজনেস স্টেকহোল্ডার, ডোমেইন এক্সপার্ট এবং ইঞ্জিনিয়ারদের একসাথে বসিয়ে বোর্ডে ব্যবসার সমস্ত ইভেন্ট (Domain Events) ক্রমানুসারে সাজানো হয়।
  2. Bounded Context নির্ধারণ: দেখা যায় একই শব্দ "Order" বিভিন্ন ডিপার্টমেন্টে ভিন্ন অর্থ বহন করে (সেলস টিমে অর্ডার মানে কোটেশন, ওয়্যারহাউসে অর্ডার মানে শিপিং প্যাকেজ)। এই ভাষাগত সীমানার ভিত্তিতে আলাদা Bounded Context (যেমন: Ordering Context, Billing Context, Inventory Context) নির্ধারণ করা হয়।
  3. প্রথম সার্ভিস নিষ্কাশন (Lowest Risk, Highest Value): সবচেয়ে কম নির্ভরশীল ও নন-ক্রিটিক্যাল কোনো সাব-ডোমেইন (যেমন: নোটিফিকেশন বা অডিট সার্ভিস) প্রথমে এক্সট্র্যাক্ট করে সিআই/সিডি ও পর্যবেক্ষণ সক্ষমতা যাচাই করা হয়।
Engineering Productivity 🔴 Senior / Lead (5-7+ Yrs)
১৪৭. DORA Metrics: ৪টি মূল মেট্রিক দিয়ে ইঞ্জিনিয়ারিং টিমের উৎপাদনশীলতা ও ডেলিভারি গতি কীভাবে পরিমাপ করবেন?

Google DevOps Research and Assessment (DORA) ফ্রেমওয়ার্কের ৪টি স্তম্ভ:

  1. Deployment Frequency (DF): প্রোডাকশনে কত ঘনঘন সফল রিলিজ হচ্ছে (এলিট টিম: দিনে একাধিকবার)।
  2. Lead Time for Changes (LTTC): একটি কোড কমিট থেকে শুরু করে প্রোডাকশনে রানিং হতে কত সময় লাগে (এলিট টিম: ১ ঘণ্টার নিচে)।
  3. Change Failure Rate (CFR): মোট ডেপ্লয়মেন্টের কত শতাংশে ত্রুটি বা হটফিক্স লাগে (এলিট টিম: ০% - ১৫%)।
  4. Time to Restore Service (MTTR): প্রোডাকশনে কোনো সার্ভিস ক্র্যাশ বা বিভ্রাট ঘটলে কত দ্রুত রিস্টোর করা যায় (এলিট টিম: ১ ঘণ্টার নিচে)।

টিমকে অতিরিক্ত কাজের চাপে পিষ্ট না করে এই ৪টি মেট্রিক স্বয়ংক্রিয়ভাবে সিআই/সিডি ড্যাশবোর্ডে ট্র্যাক করে বটলনেক দূর করা টেক লিডের মূল দায়িত্ব।

Crisis Leadership P0 🔴 Senior / Lead (5-7+ Yrs)
১৪৮. P0/P1 ক্রিটিক্যাল প্রোডাকশন আউটেজের সময় War Room ও স্টেকহোল্ডার কমিউনিকেশন ম্যানেজমেন্টের ফ্রেমওয়ার্ক কী?

২. যোগাযোগের ক্যাডেন্স (Comms Cadence): Communications Lead প্রতি ২০ মিনিটে বিজনেস টিম ও গ্রাহকদের স্ট্যাটাস পেজে আপডেট দেবেন: "সমস্যাটি শনাক্ত হয়েছে, ট্রাফিক ডাইভার্ট করে সমাধান পরীক্ষা করা হচ্ছে। পরবর্তী আপডেট দুপুর ২:২০ মিনিটে।"

৩. শান্ত মনস্তাত্ত্বিক নেতৃত্ব: প্যানিক বা আতঙ্ক দ্রুত টিমের বুদ্ধিমত্তা নষ্ট করে। টেক লিড হিসেবে শান্ত কণ্ঠে দল পরিচালনা করা এবং কোনো পূর্বানুমান ছাড়া লগ ও মেট্রিক্সের উপর ভিত্তি করে সিদ্ধান্ত নেওয়া।

FinOps Cloud Cost 🔴 Senior / Lead (5-7+ Yrs)
১৪৯. FinOps ও Cloud Cost Optimization: পারফরম্যান্স ক্ষতি না করে ক্লাউড বিল ৩০%–৫০% কীভাবে কমাবেন?

অধিকাংশ কোম্পানিতে ক্লাউড রিসোর্সের প্রায় ৪০% অপচয় হয়। একজন সিনিয়র টেক লিড যেভাবে খরচ কমান:

  1. Rightsizing Workloads: মেট্রিক্স বিশ্লেষণ করে দেখা যায় ৪-কোর ১৬GB র‍্যামের সার্ভার গড়ে মাত্র ১০% সিপিইউ ব্যবহার করছে। ইনস্ট্যান্স সাইজ কমিয়ে ২-কোর ৮GB করা।
  2. Reserved Instances / Compute Savings Plans: যেসব ডেডিকেটেড ডাটাবেজ ৩ বছর ধরে একটানা চলবে, সেগুলোতে Pay-As-You-Go না রেখে ১ বা ৩ বছরের Savings Plan নিলে বিল সরাসরি ৬০% কমে যায়।
  3. Storage Lifecycle Policies: AWS S3 বা Azure Blob এ ৩০ দিন পুরানো অডিট লগ বা ইমেজকে স্বয়ংক্রিয়ভাবে Cool এবং ৯০ দিন পর Glacier / Archive টিয়ারে পাঠিয়ে দেওয়া (স্টোরেজ বিল ৯০% কমে)।
  4. Non-production Auto-shutdown: টেস্ট ও স্টেজিং সার্ভারগুলো রাত ৮টা থেকে সকাল ৮টা পর্যন্ত এবং ছুটির দিনে স্ক্রিপ্ট দিয়ে স্বয়ংক্রিয়ভাবে শাটডাউন রাখা।

সিনিয়ররা মুখস্থ সংজ্ঞা দিয়ে কাজ করেন না, তাদের ট্রেড-অফ বোঝার ক্ষমতা যাচাই করতে হয়:

  1. রিয়েল-ওয়ার্ল্ড বাগ ট্রাবলশুটিং সিনারিও: "আমাদের সিস্টেমে ব্ল্যাক ফ্রাইডে সেলে হঠাৎ ডাটাবেজ সিপিইউ ১০০% হয়ে গেছে। আপনি কীভাবে ট্রাবলশুট শুরু করবেন? আপনার ফার্স্ট ৩টি কমান্ড কী হবে?"
  2. সিস্টেম ডিজাইন ট্রেড-অফ চ্যালেঞ্জ: "আমরা একটি গ্লোবাল রিয়েল-টাইম নোটিফিকেশন সিস্টেম বানাব। আপনি কেন কাফকা নেবেন বা কেন রেডিস পাব/সাব নেবেন? আপনার আর্কিটেকচার কোথায় ব্যর্থ হতে পারে?"
  3. কোড রিভিউ সেশন: তাদের একটি ইচ্ছা করে মেমোরি লিক ও থ্রেড আন-সেফ কোডযুক্ত পিআর দেওয়া হয়—দেখার জন্য তারা সিকিউরিটি ও কনকারেন্সি ঝুঁকিগুলো ধরতে পারে কি না।
  4. কালচারাল ও মেন্টরশিপ মাইন্ডসেট: "আপনার টিমের একজন জুনিয়র ডেভেলপার বারবার একই ভুল করছে। আপনি তাকে কীভাবে ফিডব্যাক দেবেন?"
Executive Communication 🔴 Senior / Lead (5-7+ Yrs)
১৫২. নন-টেকনিক্যাল এক্সিকিউটিভ ও সিইও-র কাছে জটিল টেকনিক্যাল চ্যালেঞ্জ ও ঝুঁকি কীভাবে তুলে ধরবেন?

নন-টেকনিক্যাল লিডারদের কাছে কোড আর্কিটেকচার, মেমোরি লিক বা ডাটাবেজ ইনডেক্সের কথা বলা অর্থহীন। তাদের ভাষা হলো: Revenue (রাজস্ব), Risk (ঝুঁকি), Cost (খরচ), এবং Time to Market (গতি)।

রূপান্তরের উদাহরণ:

  • খারাপ টেকনিক্যাল প্রেজেন্টেশন: "আমাদের ডেটাবেজ নোডে থ্রেডপুল স্টারভেশন হচ্ছে এবং আইওপস স্পাইক করায় কানেকশন ড্রপ করছে।"
  • নিখুঁত এক্সিকিউটিভ প্রেজেন্টেশন: "গত সপ্তাহে আমাদের চেকআউট পেজে ৫% ব্যবহারকারী অর্ডার সম্পন্ন করতে পারেননি, যার ফলে আনুমানিক ১২ লাখ টাকার সেলস ড্রপ করেছে। ডাটাবেজ অপ্টিমাইজেশন ও ক্যাশিং আপগ্রেড করতে ২ সপ্তাহের ইঞ্জিনিয়ারিং সময় প্রয়োজন, যা সফল হলে সেলস লস ০% এ নেমে আসবে এবং মাসিক ক্লাউড বিল ১৫% হ্রাস পাবে।"
Cross-Team Dependencies 🔴 Senior / Lead (5-7+ Yrs)
১৫৩. ৫+ ইঞ্জিনিয়ারিং টিমের ক্রস-ডিপেনডেন্সি এবং ব্লকিং ইস্যু কীভাবে Contract-First ও Mock Server দিয়ে সমাধান করবেন?

যদি মোবাইল টিম ব্যাকএন্ড এপিআই কমপ্লিট হওয়ার জন্য ৩ সপ্তাহ অপেক্ষা করে বসে থাকে, পুরো প্রজেক্টের রিলিজ ডিলে হয়ে যায়।

Contract-First এপ্রোচ:

  1. কোড লেখার আগেই OpenAPI (Swagger) বা Protocol Buffer দিয়ে উভয় টিমের মধ্যে এপিআই রিকোয়েস্ট ও রেসপন্স স্কিমা কন্ট্রাক্ট হিসেবে ফাইনাল করা হয়।
  2. Mock Server (Prism / WireMock): স্কিমার উপর ভিত্তি করে দিন ১ থেকেই একটি ফেক মক সার্ভার চালু করে দেওয়া হয় যা ডামি কিন্তু নিখুঁত স্কিমা ডেটা রেসপন্স করে।
  3. মোবাইল টিম মক সার্ভার দিয়ে ফুল UI ডেভেলপমেন্ট ও টেস্টিং সম্পন্ন করে। পরবর্তীতে ব্যাকএন্ড আসল এপিআই লাইভ করলে শুধুমাত্র বেস ইউআরএল চেঞ্জ করেই সরাসরি কানেক্ট হয়ে যায় কোনো ব্লক থাকা ছাড়াই।
Psychological Safety 🔴 Senior / Lead (5-7+ Yrs)
১৫৪. Psychological Safety কী এবং কীভাবে একটি টিমে "Blameless Engineering Culture" গড়ে তুলবেন?

Psychological Safety: এমন একটি দলগত পরিবেশ যেখানে টিমের যেকোনো সদস্য কোনো ভয় বা সংকোচ ছাড়া নতুন আইডিয়া প্রস্তাব করতে পারে, প্রশ্ন করতে পারে এবং ভুল স্বীকার করতে পারে।

বাস্তবায়নের কৌশল:

  • যদি কোনো ইঞ্জিনিয়ারের ভুলের কারণে প্রোডাকশন ডাউন হয়ে যায়, তাকে জনসমক্ষে তিরস্কার না করে সিস্টেমের সুরক্ষার ব্যর্থতা হিসেবে দেখা। "কেন আমাদের সিআই/সিডি অটোমেশন এই বাগ আটকাতে পারল না? কীভাবে টেস্ট স্যুট উন্নত করব?"
  • ভুল স্বীকার করার ক্ষেত্রে টেক লিড নিজের ভুলের উদাহরণ দিয়ে লিড করা: "আমি গত বছর ক্যাশ কনফিগারেশন মিস করায় বিভ্রাট ঘটেছিল, আসুন দেখি আমরা কীভাবে এটি থেকে শিখেছি।"
  • এতে টিমের সদস্যরা সমস্যা লুকিয়ে না রেখে দ্রুত প্রকাশ করে এবং জটিল প্রোডাকশন ইস্যু মুহূর্তেই ধরা পড়ে।
Security & Compliance 🔴 Senior / Lead (5-7+ Yrs)
১৫৫. GDPR, ISO 27001 এবং SOC 2 কমপ্লায়েন্স নিশ্চিত করতে সফটওয়্যার আর্কিটেকচারে কোন ৩টি নিয়ম মেনে চলা আবশ্যক?

এন্টারপ্রাইজ সফটওয়্যার আর্কিটেকচারের ৩টি অলঙ্ঘনীয় নিরাপত্তা স্তর:

  1. Encryption in Transit & At Rest: সমস্ত বাহ্যিক ও অভ্যন্তরীণ কমিউনিকেশন TLS 1.3 এনক্রিপশনে হতে হবে। ডাটাবেজ এবং ক্লাউড স্টোরেজে AES-256 এনক্রিপশন সক্রিয় থাকতে হবে।
  2. Data Minimization & PII Masking: ডাটাবেজে ইউজার পাসওয়ার্ড সর্বদা Argon2id বা BCrypt দিয়ে হ্যাশ করতে হবে। লগ ফাইলে ক্রেডিট কার্ড নম্বর বা ইমেইল কখনো প্লেইন টেক্সটে লেখা যাবে না (Masking / Tokenization)।
  3. Right to be Forgotten (GDPR Data Purge): ইউজার একাউন্ট ডিলিট করার আবেদন করলে ডাটাবেজের সমস্ত প্রাইমারি ও সেকেন্ডারি টেবিল থেকে তার সমস্ত ব্যক্তিগত ডেটা ৩০ দিনের ভেতর চিরতরে মুছে ফেলা অথবা সম্পূর্ণ অ্যানোনিমাইজ (Pseudonymization) করার ব্যাকগ্রাউন্ড অটোমেশন জব থাকতে হবে।

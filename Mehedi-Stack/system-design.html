সিস্টেম ডিজাইন ও এন্টারপ্রাইজ আর্কিটেকচার

৭+ বছরের সিনিয়র সফটওয়্যার ইঞ্জিনিয়ার বা সলিউশন আর্কিটেক্টের ইন্টারভিউয়ের মেক-অর-ব্রেক রাউন্ড হলো সিস্টেম ডিজাইন (System Design Round)। এই গাইডে ডিস্ট্রিবিউটেড ট্রানজ্যাকশন, মেসেজিং মেকানিক্স, ফল্ট টলারেন্স এবং ৩টি ক্লাসিক বাস্তব সিস্টেমের আর্কিটেকচারাল ব্লুপ্রিন্ট উপস্থাপন করা হলো।

১. সিস্টেম ডিজাইন ইন্টারভিউয়ের ৫-ধাপের আর্কিটেকচারাল ফ্রেমওয়ার্ক

ইন্টারভিউয়ার যখন বলে: "Design a system like Amazon / Uber / TinyURL", তখন সাথে সাথে কোড বা ডাটাবেজ টেবিল আঁকতে শুরু করা মারাত্মক ভুল! একজন সিনিয়র লিড ৫টি নিয়মতান্ত্রিক ধাপে উত্তর দেন:

ধাপ ১
Requirement Clarification

ফাংশনাল (কোর ফিচার) ও নন-ফাংশনাল রিকোয়ারমেন্টস (Latency < 50ms, 99.99% Availability, Scale)।

ধাপ ২
Capacity Estimation

QPS (Queries Per Sec), পিক ট্র্যাফিক, স্টোরেজ ক্যাপাসিটি (৫ বছরে কত টেরাবাইট), ব্যান্ডউইথ ও ক্যাশ সাইজ ক্যালকুলেশন।

ধাপ ৩
High-Level Diagram

Client → CDN → Load Balancer → API Gateway → Microservices → Cache → DB।

ধাপ ৪
Deep Dive Component Design

ডাটাবেজ স্কিমা (SQL vs NoSQL), কনকারেন্সি ও লকিং স্ট্র্যাটেজি, মেসেজ ব্রোকার, ডিস্ট্রিবিউটেড ট্রানজ্যাকশন সল্যুশন।

ধাপ ৫
Bottlenecks & Fault Tolerance

Single Points of Failure (SPOF), Rate Limiting, ডাটাবেজ রেপ্লিকেশন ও ফেইলওভার, রিট্রাই ও সার্কিট ব্রেকার।

২. CAP Theorem ও Idempotency Keys

ডিস্ট্রিবিউটেড সিস্টেমে নেটওয়ার্ক বিভাজন (Network Partition - 'P') অনিবার্য। তাই সিস্টেম ডিজাইনে আপনাকে বেছে নিতে হবে:
• CP (Consistency + Partition Tolerance): ব্যাংক এবং পেমেন্ট সিস্টেমে যদি ডাটাবেজ নোডের মধ্যে নেটওয়ার্ক ড্রপ হয়, সিস্টেম এরর দেবে কিন্তু ভুল/পুরনো ডাটা দেখাবে না। (যেমন: MongoDB with Majority Write, PostgreSQL Streaming Replication)।
• AP (Availability + Partition Tolerance): সোশ্যাল মিডিয়া ও মেসেজিংয়ে ডাটা সাময়িক অসঙ্গত হলেও সার্ভিস সবসময় রিকোয়েস্ট একসেপ্ট করবে এবং পরে Eventual Consistency দিয়ে মিলবে। (যেমন: Cassandra, DynamoDB)।

Idempotency Keys (ডুপ্লিকেট চার্জ প্রতিরোধ করা)

ডিস্ট্রিবিউটেড সিস্টেমে নেটওয়ার্ক ড্রপের কারণে ক্লায়েন্ট একই রিকোয়েস্ট একাধিকবার রি-ট্রাই করতে পারে। যদি ইউজার পেমেন্ট সাবমিট করার পর নেটওয়ার্ক টাইমআউট পায় এবং আবার সাবমিট করে, তার কার্ড থেকে দুবার টাকা কেটে যাওয়া একটি ক্যাটাষ্ট্রফিক বাগ।

সমাধান: ক্লায়েন্ট প্রতি অর্ডারে একটি ইউনিক Idempotency-Key: UUID হেডারে পাঠাবে। সার্ভার ডাটাবেজ বা Redis এ চেক করবে এই কি-টি ইতোমধ্যে প্রসেস হয়েছে কি না। যদি প্রসেস হয়ে থাকে, সে পুনরায় টাকা না কেটে পূর্বের সফল রেজাল্ট রিটার্ন করবে।

৩. Kafka বনাম RabbitMQ এবং Transactional Outbox Pattern

বৈশিষ্ট্য RabbitMQ (Smart Broker, Dumb Consumer) Apache Kafka (Dumb Broker, Smart Consumer)
মডেল Message Queue (মেসেজ পড়া শেষে কিউ থেকে ডিলিট হয়ে যায়) Distributed Append-Only Commit Log (মেসেজ স্থায়ীভাবে থাকে)
রাউটিং খুবই জটিল ও ফ্লেক্সিবল (Direct, Fanout, Topic, Headers Exchanges) টপিক এবং পার্টিশন ভিত্তিক (কী হ্যাশ দিয়ে পার্টিশন নির্ধারণ)
থ্রুপুট প্রতি সেকেন্ডে হাজার হাজার মেসেজ (কম্প্লেক্স রাউটিং) প্রতি সেকেন্ডে লাখ লাখ মেসেজ (সিকোয়েনশিয়াল ডিস্ক I/O)
রিপ্লে / রি-রিড সম্ভব নয় (একবার ডেলিভারি শেষে নেই) সহজেই সম্ভব (অফসেট পিছিয়ে দিয়ে আবার পড়া যায়)
Dual-Write Problem ও Transactional Outbox Pattern

যখন আপনার সার্ভিস একটি নতুন অর্ডার ডাটাবেজে সেভ করে এবং একই সাথে কাফকাতে OrderPlacedEvent পাঠাতে চায়:
যদি ডাটাবেজ সেভ সফল হয় কিন্তু কাফকা ডাউন থাকার কারণে মেসেজ পাবলিশ ফেইল করে, তাহলে সিস্টেম ইনকনসিস্টেন্ট হয়ে যায়।

Transactional Outbox সল্যুশন:
১. সরাসরি কাফকাতে না পাঠিয়ে, একই ডাটাবেজ ট্রানজ্যাকশনে Orders টেবিল এবং একটি OutboxMessages টেবিলে ইভেন্টটি সেভ করুন (Atomic Transaction - দুটিই সফল হবে নয়তো রোলব্যাক)।
২. একটি ব্যাকগ্রাউন্ড মেসেজ রিলে প্রসেস (যেমন Debezium CDC অথবা .NET BackgroundService) Outbox টেবিল থেকে আনপ্রসেসড মেসেজগুলো পড়ে কাফকাতে পুশ করে এবং সফল হলে আউটবক্স রো-কে প্রসেসড মার্ক করে।

Saga Pattern: ডিস্ট্রিবিউটেড ট্রানজ্যাকশন

মাইক্রোসার্ভিসে প্রতি সার্ভিসের আলাদা ডাটাবেজ থাকে (Database-per-service), তাই ক্লাসিক ACID ট্রানজ্যাকশন কাজ করে না। Saga প্যাটার্ন লোকাল ট্রানজ্যাকশনের একটি সিরিজ চালায়:

  • Choreography (ইভেন্ট ড্রাইভেন): সার্ভিসগুলো একে অপরের ইভেন্ট শুনে পরবর্তী কাজ করে (ছোট প্রজেক্টে ভালো, বড় হলে ট্র্যাকিং অসম্ভব)।
  • Orchestration (সেন্ট্রাল কোঅর্ডিনেটর): একটি সেন্ট্রাল অর্কেস্ট্রেটর (যেমন MassTransit Saga State Machine) ধাপে ধাপে সার্ভিসকে কমান্ড পাঠায়। যদি ৩য় ধাপে পেমেন্ট ফেইল করে, অর্কেস্ট্রেটর পূর্ববর্তী ধাপগুলোতে Compensating Transaction পাঠিয়ে অর্ডার রোলব্যাক করে (যেমন ইনভেন্টরি আনলক করা)।

৪. সার্কিট ব্রেকার (Circuit Breaker) ও রেট লিমিটার

যদি ডাউনস্ট্রিম পেমেন্ট গেটওয়ে স্লো বা ডাউন হয়ে যায়, ক্লায়েন্টের সব রিকোয়েস্ট সেখানে আটকে থাকবে এবং ক্যাসকেডিং ফেইলিওর ঘটাবে। Circuit Breaker (Polly) এর ৩টি স্টেট থাকে:

Closed (নরমাল)

রিকোয়েস্ট স্বাভাবিকভাবে পাস হয়। কোনো ফেইলিওর ট্র্যাকিং কাউন্টার চালু থাকে।

Open (সার্কিট ব্রেক)

ফেইলিওর রেট (যেমন ৫০%) অতিক্রম করলে সার্কিট ওপেন হয়। ডাউনস্ট্রিমে কোনো কল না পাঠিয়ে তাৎক্ষণিক ফলব্যাক এরর দেয়।

Half-Open (টেস্টিং)

নির্ধারিত সময় পর ট্রায়াল হিসেবে ১-২টি রিকোয়েস্ট পাঠায়। সফল হলে ক্লোজড, ফেইল হলে আবার ওপেন স্টেটে ফেরে।

Token Bucket অ্যালগরিদম (Rate Limiting)

একটি বাকেটে প্রতি সেকেন্ডে নির্দিষ্ট হারে টোকেন যোগ হয় (যেমন ১০০ টোকেন/সেকেন্ড)। প্রতিটি আগত রিকোয়েস্ট বাকেট থেকে ১টি টোকেন সংগ্রহ করে এক্সিকিউট হয়। যদি বাকেটে টোকেন না থাকে, সার্ভার HTTP 429 Too Many Requests রিটার্ন করে। এটি সাময়িক ট্র্যাফিক বার্স্ট (Traffic Burst) চমৎকারভাবে নিয়ন্ত্রণ করতে পারে।

৫. রিয়েল-ওয়ার্ল্ড সিস্টেম ডিজাইন কেস স্টাডিজ

কেস ১: Flash Sale / High-Concurrency Order System

Critical Scale

চ্যালেঞ্জ: মাত্র ১,০০০টি আইটেম বিক্রির জন্য ১০ লাখ মানুষ এক সেকেন্ডে "Buy Now" বাটনে ক্লিক করে। ডাটাবেজে ওভারসেলিং বা ক্র্যাশ ছাড়াই কীভাবে সামলাবেন?

আর্কিটেকচারাল সল্যুশন:
  1. CDN & Static Asset Caching: প্রোডাক্টের ইমেজ এবং ডেসক্রিপশন পেজ সম্পূর্ণ ক্লাউডফ্লেয়ার/এডাব্লিউএস ক্লাউডফ্রন্টে ক্যাশড থাকবে (মেইন সার্ভারে ০ ট্র্যাফিক)।
  2. Rate Limiter & Virtual Waiting Room: API Gateway তে টোকেন বাকেট দিয়ে অতিরিক্ত ট্র্যাফিক ড্রপ বা কিউতে পাঠানো।
  3. Redis Lua Scripting (Pre-Deduct Stock): ডাটাবেজে সরাসরি হিট না করে Redis এ স্টক ডিক্রিমেন্ট করা: if redis.call('get', key) > 0 then return redis.call('decr', key) else return 0 end (অ্যাটমিক এবং মিলিসেকেন্ড গতি)।
  4. Async Order Creation via Kafka: যারা স্টক পেয়েছে তাদের রিকোয়েস্ট কাফকা কিউতে পাঠানো হবে। ব্যাকগ্রাউন্ড ওয়ার্কার সার্ভিস ডাটাবেজে অর্ডার এন্ট্রি তৈরি করবে।
  5. Payment Reconciliation: পেমেন্টের জন্য ১০ মিনিট স্টক রিজার্ভেশন টাইমআউট থাকবে। ফেইল হলে Redis এ স্টক ফেরত যাবে।

কেস ২: High-Scale URL Shortener (TinyURL)

High Throughput

চ্যালেঞ্জ: ১০০ মিলিয়ন নতুন ইউআরএল প্রতি মাসে তৈরি হবে। রিড ট্রাফিক রাইটের ১০০ গুণ বেশি। লেটেন্সি < ১০ মিলিসেকেন্ড।

আর্কিটেকচারাল সল্যুশন:
  • Base62 Encoding: [a-z, A-Z, 0-9] এর ৭ ক্যারেক্টার দিয়ে 62^7 = 3.5 ট্রিলিয়ন ইউনিক শর্ট কোড তৈরি করা সম্ভব।
  • Key Generation Service (KGS): রিকোয়েস্টের সময় হ্যাশ তৈরি করলে কলিশন হ্যান্ডলিং জটিল হয়। তাই একটি ডেডিকেটেড KGS ব্যাকগ্রাউন্ডে কোটি কোটি ইউনিক ৭-ক্যারেক্টার স্ট্রিং তৈরি করে প্রস্তুত রাখবে।
  • Aggressive Caching: ৮০-২০ রুলে টপ ২০% হট ইউআরএল Redis ক্যাশে থাকবে। ক্যাশ হিট রেশিও ৯৫%+ থাকায় ডাটাবেজ চাপমুক্ত থাকবে।

কেস ৩: Real-Time Push Notification Engine

Event Driven

কোটি কোটি ইউজারের ডিভাইসে রিয়েল-টাইমে নোটিফিকেশন পুশ করা (ওয়েব, মোবাইল, এসএমএস, ইমেইল)।

আর্কিটেকচারাল সল্যুশন:

SignalR + Redis Backplane: একাধিক ওয়েব সার্ভার থাকলে ক্লায়েন্টের WebSocket কানেকশন যেকোনো নোডে থাকতে পারে। Redis Pub/Sub ব্যাকপ্লেন হিসেবে কাজ করে সমস্ত সার্ভার নোডের মধ্যে মেসেজ রাউট করে।
Kafka Priority Queues: ওটিপি ও ট্রানজ্যাকশনাল নোটিফিকেশন হাই-প্রায়োরিটি পার্টিশনে প্রসেস হবে এবং মার্কেটিং নোটিফিকেশন লো-প্রায়োরিটি কিউতে রেট-লিমিট হয়ে পাঠানো হবে।

একটি ডিস্ট্রিবিউটেড মাইক্রোসার্ভিস আর্কিটেকচারে অর্ডার তৈরি হওয়ার পর পেমেন্ট সার্ভিস ও ইনভেন্টরি সার্ভিসের মধ্যে ডেটা কনসিস্টেন্সি বজায় রাখার সবচেয়ে স্কেলেবল ইন্ডাস্ট্রি-স্ট্যান্ডার্ড সমাধান কোনটি?

এন্টারপ্রাইজ ডাটাবেজ আর্কিটেকচার ও অপ্টিমাইজেশন

একটি প্রোডাকশন সিস্টেম ধীরগতির হওয়ার ৯০% কারণ থাকে অপরিকল্পিত ডাটাবেজ ডিজাইন, মিসিং বা ভুল ইনডেক্স এবং কনকারেন্সি লকিং ব্লকেজ। এই গাইডে SQL Server, PostgreSQL এবং Oracle এর জটিল ইন্টারনালস, কুয়েরি এক্সিকিউশন প্ল্যান ও রিয়াল-ওয়ার্ল্ড টিউনিং কৌশল বিশদভাবে উন্মোচন করা হলো।

১. SQL Server B-Tree ইনডেক্সিং ও Covering Index

SQL Server এ ডেটা ৮ KB সাইজের পেজ (Page) আকারে সংরক্ষিত থাকে। ইনডেক্স হলো একটি B-Tree (Balanced Tree) স্ট্রাকচার।

Clustered Index

একটি টেবিলে শুধুমাত্র একটিই Clustered Index থাকতে পারে। কারণ এটি ডাটার ফিজিক্যাল বিন্যাস সরাসরি নির্ধারণ করে। এর লিফ নোড (Leaf Node) স্বয়ং সম্পূর্ণ ডেটা রো ধারণ করে।

Non-Clustered Index

একটি টেবিলে একাধিক থাকতে পারে। এর লিফ নোডে সম্পূর্ণ ডাটা থাকে না, বরং কী-কলাম এবং মূল রো-এর পয়েন্টার (RID বা Clustered Key) থাকে।

Covering Index ও INCLUDE কলামের শক্তি

যখন কোনো কুয়েরি এমন কলাম চায় যা Non-Clustered ইনডেক্সে নেই, ডাটাবেজ ইঞ্জিন মূল টেবিলে জাম্প করতে বাধ্য হয়—যাকে বলে Key Lookup। কোটি কোটি রো-এর টেবিলে হাজার হাজার Key Lookup সার্ভারের আই/ও (I/O) ধ্বংস করে ফেলে।

সমাধান: Covering Index: কুয়েরির WHERE ক্লজের কলামকে ইনডেক্স কী-তে রাখুন এবং SELECT এর কলামগুলোকে INCLUDE ক্লজে যোগ করুন:
CREATE NONCLUSTERED INDEX IX_Orders_Cust ON Orders(CustomerId) INCLUDE (OrderDate, TotalAmount, Status);
এর ফলে কুয়েরি সম্পূর্ণভাবে ইনডেক্স পেজ থেকেই মিটে যায় (Zero Key Lookup)!

২. Execution Plan ডিকোড করা: Seek vs Scan ও Join মেকানিক্স

ইন্টারভিউতে কুয়েরি অপ্টিমাইজেশন প্রশ্ন আসলে এক্সিকিউশন প্ল্যানের এই মূল অপারেটরগুলোর পার্থক্য জানা বাধ্যতামূলক:

অপারেটর ধরন ও কস্ট কেন ঘটে এবং কী করবেন
Index Seek সুপার ফাস্ট (O(log N)) B-Tree এর রুট থেকে ট্রাভার্স করে সরাসরি কাঙ্ক্ষিত রো খুঁজে নেয়। আইডিয়াল কেস।
Index / Table Scan ভীষণ স্লো (O(N)) পুরো টেবিল বা ইনডেক্সের প্রতিটি পেজ এক মাথা থেকে অন্য মাথা পর্যন্ত পড়ে। WHERE ক্লজে ইনডেক্স না থাকলে বা ফাংশন কল করলে (SARGable না হলে) ঘটে।
Key / RID Lookup মাঝারি থেকে মারাত্মক ক্ষতিকর নন-ক্লাস্টার্ড ইনডেক্স হিট করার পর বাকি কলাম আনতে মূল পেজে যায়। Covering Index বানিয়ে সমাধান করুন।
Nested Loops Join একটি ছোট টেবিল ও একটি ইনডেক্সড বড় টেবিল বাইরের টেবিলের প্রতিটি রো-এর জন্য ভেতরের টেবিলের ইনডেক্সে দ্রুত সিঙ্ক করে। OLTP ট্রানজ্যাকশনে সেরা।
Hash Match Join দুটো বড় আন-ইনডেক্সড টেবিল মেমোরিতে হ্যাশ টেবিল বানায়। মেমোরি শর্ট পড়লে TempDB তে স্পিল করে এবং সিস্টেম ফ্রিজ করায়।
Parameter Sniffing সমস্যা:

Stored Procedure যখন প্রথমবার রান হয়, তখন যে প্যারামিটার পাঠানো হয়েছিল তার জন্য অপটিমাইজার একটি প্ল্যান ক্যাশ করে রাখে। যদি সেই প্যারামিটার মাত্র ৫টি রো রিটার্ন করত, কিন্তু পরবর্তী কলে অন্য প্যারামিটার ৫ লাখ রো রিটার্ন করে, পুরনো ইনডেক্স সিক প্ল্যানটি মারাত্মক দুর্যোগ তৈরি করে।
সমাধান: OPTION (RECOMPILE) অথবা OPTION (OPTIMIZE FOR (@param UNKNOWN)) ব্যবহার করা।

৩. Concurrency Isolation Levels ও Deadlock সমাধান

ডাটাবেজে কনকারেন্সি নিয়ন্ত্রণ করার জন্য ACID প্রোপার্টির 'I' (Isolation) এর বিভিন্ন লেভেল রয়েছে:

  • Read Uncommitted: Dirty Read হতে পারে। আন-কমিটেড ডেটাও পড়ে ফেলে।
  • Read Committed (ডিফল্ট): Dirty Read হয় না, তবে Non-Repeatable Read হতে পারে। রিড করার সময় শেয়ার্ড লক নেয় এবং রিড শেষেই লক ছেড়ে দেয়।
  • Repeatable Read: ট্রানজ্যাকশন শেষ না হওয়া পর্যন্ত শেয়ার্ড লক ধরে রাখে। ফলে অন্য কেউ আপডেট করতে পারে না, তবে নতুন রো ইনসার্ট হলে Phantom Read হতে পারে।
  • Serializable: রেঞ্জ লক (Key-Range Lock) নেয়। সম্পূর্ণ কনসিস্টেন্ট কিন্তু সর্বোচ্চ ব্লকিং ঘটায়।
  • RCSI (Read Committed Snapshot Isolation): এন্টারপ্রাইজ সিস্টেমের গেম চেঞ্জার! লক ব্যবহারের বদলে TempDB-তে ডেটার ভার্সন (Row Versioning) রাখে। "Readers never block Writers, and Writers never block Readers!"
Deadlock কীভাবে ডিবাগ ও প্রতিরোধ করবেন?

যখন ট্রানজ্যাকশন A অবজেক্ট X লক করে Y-এর জন্য অপেক্ষা করছে, এবং একই সাথে ট্রানজ্যাকশন B অবজেক্ট Y লক করে X-এর জন্য অপেক্ষা করছে, তখন ডেডলক ঘটে। SQL Server এর Deadlock Monitor থ্রেড প্রতি ৫ সেকেন্ডে রান করে এবং কম খরুচে ট্রানজ্যাকশনটিকে Victim বানিয়ে মেরে ফেলে (Error 1205)।

প্রতিরোধ কৌশল:
১. সব ট্রানজ্যাকশনে একাধিক টেবিলে ডেটা এক্সেসের সিকোয়েন্স হুবহু একই অর্ডারে রাখুন (যেমন: সবসময় আগে Orders তারপর OrderDetails)।
২. কুয়েরিতে অপ্রয়োজনীয় দীর্ঘ ট্রানজ্যাকশন রাখবেন না (নেটওয়ার্ক কল বা এপিআই কল ট্রানজ্যাকশনের বাইরে রাখুন)।
৩. Extended Events বা SQL Profiler এর `xml_deadlock_report` থেকে ডেডলক গ্রাফ দেখে মিউচুয়াল কনফ্লিক্টিং ইনডেক্স সংশোধন করুন।

৪. PostgreSQL MVCC, Tuple Bloat এবং VACUUM আর্কিটেকচার

PostgreSQL এর সবচেয়ে পাওয়ারফুল অথচ মিসআন্ডারস্টুড ফিচার হলো MVCC (Multi-Version Concurrency Control)। Postgres এ যখন কোনো রো UPDATE করা হয়, ডাটাবেজ ইঞ্জিন কিন্তু আগের রো-টিকে সরাসরি এডিট করে না!
১. এটি মূল রো-টিকে Dead Tuple হিসেবে মার্ক করে (xmax ফিল্ডে ট্রানজ্যাকশন আইডি বসিয়ে)।
২. পেজে নতুন ভ্যালু সহ একটি ব্র্যান্ড নিউ Live Tuple ইনসার্ট করে।

Table Bloat এবং Autovacuum টিউনিং

যদি একটি টেবিলে প্রতি মিনিটে লাখ লাখ আপডেট ও ডিলিট হয়, কোটি কোটি ডেড টাপল ডিস্ক দখল করে রাখবে। কুয়েরি করার সময় ইঞ্জিনকে অপ্রয়োজনীয় ডেড টাপলও স্ক্যান করতে হয়। একে বলে Table Bloat।

VACUUM এর ভূমিকা: VACUUM ডেড টাপলগুলো মুছে ফেলে সেই স্পেস ভবিষ্যতের নতুন রো লেখার জন্য রিইউজেবল করে। কিন্তু এটি ওএস-কে ডিস্ক স্পেস ফিরিয়ে দেয় না। ডিস্ক স্পেস ফিরিয়ে দিতে VACUUM FULL লাগে যা টেবিল এক্সক্লুসিভ লক করে।
সিনিয়র ডিবিএ টিপ: ডিফল্ট autovacuum সেটিংস খুব রক্ষণশীল থাকে। হাই-রাইট টেবিলের জন্য `autovacuum_vacuum_scale_factor = 0.05` (৫% ডেড টাপলেই ভ্যাকুয়াম চলবে) এবং `autovacuum_vacuum_cost_limit = 2000` কনফিগার করুন।

Postgres EXPLAIN (ANALYZE, BUFFERS) ডিকোড করা

সাধারণ `EXPLAIN` শুধুমাত্র প্ল্যানারের আনুমানিক কস্ট দেখায়। কিন্তু EXPLAIN (ANALYZE, BUFFERS) কুয়েরিটিকে প্রকৃতপক্ষে ডাটাবেজে রান করায় এবং মেমোরির আসল অবস্থা জানায়:

  • Buffers: shared hit: ডাটা Postgres এর Shared Buffers (RAM) থেকে সরাসরি পেয়ে গেছে (সুপার ফাস্ট)।
  • Buffers: shared read: ডাটা র‍্যামে ছিল না, ওএস ডিস্ক থেকে পড়তে হয়েছে (স্লো I/O)।
  • Sort Method: external merge Disk: কুয়েরির অর্ডার বা গ্রুপিংয়ের জন্য work_mem সাইজ যথেষ্ট ছিল না, তাই ডিস্কে টেম্প ফাইল তৈরি করে সর্ট হয়েছে। এটি দেখলেই বুঝবেন সেশনের জন্য SET work_mem = '64MB'; বাড়ানো প্রয়োজন।
PostgreSQL JSONB বনাম JSON এবং GIN ইনডেক্স

পস্টগ্রেসের json টাইপ হুবহু টেক্সট হিসেবে ডাটা রাখে (ইনসার্ট দ্রুত, কুয়েরি স্লো কারণ প্রতিবার পার্স করতে হয়)। আর jsonb ডাটাকে বাইনারি ফরম্যাটে ডিকম্পোজ করে রাখে (ইনসার্টে সামান্য ওভারহেড, কিন্তু কুয়েরি ও ইনডেক্সিং বিদ্যুৎগতি)।

GIN (Generalized Inverted Index): JSONB ডকুমেন্টের ভেতরের যেকোনো নেস্টেড ফিল্ড দ্রুত কুয়েরি করার জন্য GIN ইনডেক্স ব্যবহার করা হয়:
CREATE INDEX idx_user_meta ON Users USING GIN (metadata jsonb_path_ops);
এটি `WHERE metadata @> '{"role": "admin"}'` কুয়েরিতে মিলিসেকেন্ডে রেজাল্ট দেয়!

PgBouncer কেন পস্টগ্রেসে বাধ্যতামূলক?

MySQL বা SQL Server থ্রেড-বেসড কানেকশন ব্যবহার করে। কিন্তু PostgreSQL প্রতিটি ক্লায়েন্ট কানেকশনের জন্য অপারেটিং সিস্টেমে একটি সম্পূর্ণ আলাদা Forked Process তৈরি করে, যা প্রতি কানেকশনে ১০ MB পর্যন্ত মেমোরি দখল করে। যদি ডটনেট বা জাভা অ্যাপ্লিকেশন থেকে ১,০০০ ডিরেক্ট কানেকশন আসে, সার্ভার ক্র্যাশ করবে!
PgBouncer: এটি একটি লাইটওয়েট কানেকশন পুলার। এটি Transaction Pooling Mode এ মাত্র ৫০টি আসল ডাটাবেজ প্রসেস দিয়ে বাইরের ১০,০০০ ওয়েব ক্লায়েন্টের রিকোয়েস্ট অনায়াসে হ্যান্ডেল করতে পারে।

৫. Oracle Database আর্কিটেকচার ও এন্টারপ্রাইজ PL/SQL

ব্যাংক, টেলিকম এবং বৃহৎ বহুজাতিক সংস্থায় ওরাকল ডাটাবেজ সবচেয়ে বেশি ব্যবহৃত হয়। ৭+ বছর অভিজ্ঞতায় ওরাকলের ইন্টারনাল মেমোরি ও পিএল/এসকিউএল কোড অপ্টিমাইজেশন জানা একটি বিশাল শক্তি।

SGA (System Global Area)

ওরাকল ইনস্ট্যান্সের শেয়ার্ড মেমোরি। এর ভেতর থাকে Database Buffer Cache (ডাটা পেজ), Shared Pool (লাইব্রেরি ক্যাশ ও ডিকশনারি ক্যাশ যেখানে SQL পার্স ট্রি থাকে), এবং Redo Log Buffer।

PGA (Program Global Area)

প্রতিটি ওরাকল সার্ভার প্রসেসের জন্য নন-শেয়ার্ড প্রাইভেট মেমোরি। এখানে সর্টিং (Sort Area), হ্যাশ জয়েন এবং কার্সরের স্টেট সংরক্ষিত থাকে।

BULK COLLECT ও FORALL (Context Switching এলিমিনেট করা)

যখন আপনি সাধারণ PL/SQL লুপে FOR r IN (SELECT * FROM LargeTable) LOOP INSERT ... END LOOP; চালান, প্রতি রো প্রসেস করার সময় পিএল/এসকিউএল রানটাইম ইঞ্জিন এবং এসকিউএল ইঞ্জিনের মধ্যে Context Switching ঘটে। ১০ লাখ রো-এর জন্য ১০ লাখ বার কনটেক্সট সুইচ হলে স্ক্রিপ্ট ঘণ্টার পর ঘণ্টা আটকে থাকে।

সিনিয়র সল্যুশন: BULK COLLECT দিয়ে মেমোরি অ্যারেতে একবারে ডেটা লোড করুন এবং FORALL স্টেটমেন্টে এক সিঙ্গেল ব্যাচে ডাটাবেজ ইঞ্জিনে পুশ করুন:

High-Performance PL/SQL
DECLARE TYPE t_emp_list IS TABLE OF employees%ROWTYPE; l_emps t_emp_list; CURSOR cur_emp IS SELECT * FROM employees WHERE department_id = 10; BEGIN OPEN cur_emp; LOOP -- একবারে ১,০০০ রো ব্যাচ আকারে মেমোরিতে আনা (Zero Row-by-Row Switching) FETCH cur_emp BULK COLLECT INTO l_emps LIMIT 1000; -- সিঙ্গেল রাউন্ডট্রিপে পুরো ব্যাচ প্রসেস FORALL i IN 1..l_emps.COUNT SAVE EXCEPTIONS UPDATE emp_salaries SET salary = salary * 1.1 WHERE emp_id = l_emps(i).emp_id; EXIT WHEN cur_emp%NOTFOUND; END LOOP; CLOSE cur_emp; COMMIT; END;
ORA-04091: Mutating Table Error কীভাবে সমাধান করবেন?

যখন কোনো Row-Level Trigger (BEFORE/AFTER INSERT/UPDATE FOR EACH ROW) চলাকালীন একই ট্র্রিগারটি যে টেবিলে ফায়ার হয়েছে সেই টেবিল থেকেই SELECT কুয়েরি করার চেষ্টা করে, ওরাকল এই এক্সেপশন দেয়। কারণ রো-টি এখনো ট্রানজ্যাকশনে ইন-ফ্লাইট অবস্থায় রয়েছে।
সমাধান:
১. Oracle 11g+ এর Compound Trigger ব্যবহার করা (যার BEFORE STATEMENT, BEFORE EACH ROW, AFTER STATEMENT সেকশন রয়েছে)।
২. যদি শুধু লগ টেবিলে অডিট হিস্ট্রি লিখতে হয়, তাহলে PRAGMA AUTONOMOUS_TRANSACTION ব্যবহার করে মূল ট্রানজ্যাকশনের বাইরে একটি সম্পূর্ণ স্বাধীন ট্রানজ্যাকশনে কাজ করা।

৬. Redis ক্যাশিং আর্কিটেকচার, Stampede ও RedLock

উচ্চ ট্রাফিকের ডাটাবেজের সামনে রেডিস ক্যাশ ব্যবহার করা হয়। তবে ৭+ বছরের সিনিয়র ইঞ্জিনিয়ার হিসেবে আপনাকে ক্যাশের এই বিপর্যয়গুলো সামলানোর আর্কিটেকচার জানতে হবে:

Cache Stampede

একটি হট কি (যেমন ট্র্যাফিক হট সেল) এক্সপায়ার হওয়ার সেকেন্ডে হাজার হাজার রিকোয়েস্ট একযোগে ডাটাবেজে হিট করে ডাটাবেজ ক্র্যাশ করায়।

Cache Avalanche

একই সময়ে নির্ধারিত টিটিএল (TTL) এর শত শত কি এক সাথে এক্সপায়ার হয়ে সব ট্র্যাফিক একসাথে ডাটাবেজে আছড়ে পড়ে। সমাধান: TTL এ Random Jitter যোগ করা।

Cache Penetration

এমন আইডি দিয়ে রিকোয়েস্ট যা ডাটাবেজেও নেই। ক্যাশ মিস হয়ে প্রতিবার ডাটাবেজে যায়। সমাধান: Bloom Filter বা Null Caching।

RedLock (ডিস্ট্রিবিউটেড লক):

একাধিক মাইক্রোসার্ভিস ইনস্ট্যান্স যখন একটি শেয়ার্ড রিসোর্স (যেমন একই ইনভেন্টরি স্টক আপডেট) এক্সেস করে, লোকাল C# lock কাজ করে না। তখন রেডিসের SET resource_name my_random_value NX PX 30000 দিয়ে একটি ডিস্ট্রিবিউটেড লক নেওয়া হয়। কাজ শেষ হলে Lua স্ক্রিপ্ট দিয়ে নিশ্চিত করা হয় যে লকটি কেবলমাত্র সেই প্রসেসই রিলিজ করছে যে এটি একোয়ার করেছিল।
